## 2. 【新发现】P1-1：行内散文式台账带退款词被方向兜底翻转成收入

**现象**【生产实测】：-heavy 账号记录「周末出行开销：车费 46，门票 120，午餐 88，纪念品退款 -30，合计 224」→ 分拣为 **income 224**（真值 expense 224）。连锁污染：

- 「我今天一共花了多少钱？」→ 支出 ¥886 / 收入 ¥674（真值：支出 ¥1110 / 收入 ¥450，即 224 被整体挪到收入侧）；
- 周报「收支合计」同样给出 收入 ¥674 的虚假结余。【生产实测】

**根因**【本地测试】【源码检查】：该形态是单行散文式台账（全角逗号内联，无换行）。`parseLedgerCore` 对其返回 null（vitest 本地复现），于是 R196 在 `fixFinanceDirection` 里加的「认得的台账跳过方向兜底」守卫不生效；内容含「退款」（INCOME_DIRECTION_RE）而无「花了/买了」类支出动词（「开销」不在 EXPENSE_DIRECTION_RE 里），R118 方向兜底把模型的 expense 判定确定性翻转成 income——与 R195 P1-1 完全同类，只是换了台账形态。对照组：同批三行 CSV 台账「数码配件账单,退货退款,-59」→ expense 49 正确（解析器认得，多行形态已被 R196 守住）。

**建议（只论证不改码）**：R196 的修复方向正确但守卫的"台账识别"覆盖面不足。可选收口：(a) `fixFinanceDirection` 对「内容含 ≥2 个『名目+金额』对且含合计词」的单行内容也跳过兜底（行内台账嗅探，不必完整解析）；(b) 或 EXPENSE_DIRECTION_RE 补「开销/花销/支出」名词词面——但这会改变兜底语义（名词≠动作证据），风险更高，倾向 (a)。修复后应把该形态并入 R194 建立的台账形态用例集。

**信号可行性验证**【本地测试】：`financeTopicTerms("团建烧烤多少钱？")` = null（FINANCE_WORD_RE 门槛拦截）；而既有 `ledgerRowsMatching`（R196 P2-1 已上线）对「打印纸」「团建烧烤」精确返回行级命中（120 / 286.5），对「身高」等非财务词返回空——**行级命中信号已存在且判别力足够**。

**设计建议**：新增一条**数据门控**的短问法路由，与全账兜底解耦：

1. 触发条件：SUBSET_AGG_RE 命中（多少钱/多少）但 FINANCE_WORD_RE 不命中；
2. 用与 financeTopicTerms 相同的 STRIP 管道提取候选主题词；
3. 门控：候选词对用户财务笔记（标题/正文 LIKE）或 `ledgerRowsMatching` 行级命中 **≥1 条**才路由到 buildFinanceSubsetAnswer（行级口径）；
4. 零命中一律走普通召回，**永不**落到全账合计 fail-closed 兜底——这正是 R196 担心的误触发路径，被门控天然排除（「身高多少」不会命中任何财务行）；
5. 台账行级极值问法同理：主题词命中台账时，用 `ledgerTableRows` 的行金额做确定性排序。
6. 实施前置：把短问法 ×（命中/不命中）× 行级/单笔 约 20 个样本并入 ask-eval 固定评估集，先锁行为再实现（SOP-02）。

风险与代价：候选词提取自由度高（「多少钱」前的任意残片），需复用 degradeFinanceSubsetTerms 的降级链并保留 2-8 字白名单正则；门控查询多一次 LIKE + 行级解析，成本可忽略（子集路径本就做同样的事）。
