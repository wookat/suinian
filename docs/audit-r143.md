## 2. 附件渲染盘点（已知问题确认）

| 附件类型 | Web | Android | 结论 |
|---|---|---|---|
| 导入图片（flomo） | 仅文字标记 `【图片：food.jpg】`，无内联预览【生产实测，截图 ss_262bc993】 | 同为文字标记【源码走读 NoteCard.kt】 | **P1-1** |
| 原生图片笔记（上传/拍照） | 卡片显示 AI 描述文本 + 展开描述；**不显示原图**【生产实测】 | 同：描述 +"查看图片描述"，无原图【生产实测 and18】 | P1-1 同源 |
| 语音笔记 | 显示转写文本；无播放器 | 显示"语音转写"文本；无播放控件【生产实测 and17】 | 转写即价值主张，播放缺失定 P2 |
| 文件笔记 | 文件名/大小元信息 + 下载 + 提取失败重试【源码走读 note-card.tsx】 | 元信息 + 下载【源码走读】 | 现状可接受 |

**P1-1（体验缺陷，影响核心主线"可靠找回"的完整度，不阻断）：全端不渲染附件原图。**
原图已在 R2、可下载、描述可搜索——"找回"的数据层是通的；但用户找回一张照片时看到的是一段 AI 描述而非照片本身，与"可靠找回"的直觉承诺不符。flomo 迁移用户首屏即见一排 `【图片：xx】` 文字，第一印象受损。

**统一附件展示设计建议（如无必要勿增实体——复用现有 `/api/notes/:id/file` 与 attachments 表，不新增实体）：**
1. 卡片内联缩略图：图片附件直接 `<img>` 指向现有 file 端点（加 `?w=` 缩略参数可后续再做），点击看大图；AI 描述降级为图片下方的可折叠辅助文本，而非主体。
2. 导入标记升级：`【图片：name】` 标记在渲染层反查同笔记 attachments 按文件名匹配，替换为内联图；无匹配才回退文字。解析层已把 name 与 asset 关联，纯展示层改造，零 schema 变更。
3. 语音附件：转写文本保持主体，附一个原生 `<audio>` 播放条（同一 file 端点）。
4. 三端（Web/Android）用同一优先级规则：原件可见 > 提取物（描述/转写）> 元信息，保证心智一致。

## 5. 设计质疑（2 个未审流程深挖）

### 5.1 账号与凭证生命周期：忘记密码 = 永久丢失全部数据
【源码走读+生产实测】注册仅 name+password，无邮箱/手机绑定；后端**不存在任何找回/重置密码端点**（grep 全仓无 reset/forgot/recover/email 路由）；token 可轮换但轮换本身需先登录。
- 是否真的最适合？**不是。** 产品承诺"可靠找回"，但账号层面一次遗忘即全量数据不可找回，与核心主线自相矛盾，且用户量增长后必然成为最高频客诉。
- 更好的方式（按"勿增实体"排序）：① 最小改动——注册时可选留一个恢复邮箱字段 + 一条带时效的重置链接（一个字段一个端点，不引入完整 IAM）；② 引导用户定期下载备份 zip 作为兜底（已有 /api/backup，成本为零，只差 UI 提示）；③ 微信绑定已存在（wechat_mp_bindings 表），可把"已绑定微信可扫码重置"作为零新增实体的恢复通道。
- 建议定级：**P1-2**（数据安全性质的产品设计缺陷，推广前应有至少一条恢复通道或明确告知）。

### 5.2 线索（聚类）从生成到消费的闭环：口径过窄+过保守
【源码走读+生产实测】仅 `idea/collect` 两类参与聚类（THREAD_CATEGORIES）；加入阈值 SIM_JOIN=0.76、确认下限 0.62（注释载明为 84.2% 配对精度调参结果）。实测 15 条多主题语料仅聚出 1 条线索（2 成员）。
- 是否真的最适合？精度优先方向正确（错聚比漏聚伤害大），但两点值得质疑：① `todo/log` 类被整体排除——"装修"这类真实项目的待办与想法天然同串，现口径把项目叙事拦腰截断；② 用户看不到"为什么这些笔记没聚成线索"，漏聚是静默的，无法反馈。
- 更好的方式：① 类别不作硬门槛，改为 todo/log 只能"被吸入"已有线索、不能发起新线索（复用现有 confirm 流程，无新实体）；② 线索页加一个"可能相关"弱建议区（sim ∈ [0.62,0.76) 已在代码中计算，仅缺展示），让用户点选确认，把漏聚变成可交互的召回。
- 建议定级：设计建议（不定 P 级，功能正确性无缺陷）。
