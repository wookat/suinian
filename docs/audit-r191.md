## 1. R190 复核（生产实测，-fin / -cluster 账号）

### 1.1 极值/序数/台账全组合 ⚠️ 部分收口，新 P1

20 问全组合实测（语料：单笔支出 459/155/88/68/36 + 多行台账合计 454，其中台账明细行最大 368.5）。结果：15/20 正确，其中 R190 声称修复的问法全部确证：

- 「最贵的一笔花销」「花得最多的一笔」「单笔最贵…多少钱/买的什么」「花钱最狠的一笔」「逐笔看哪笔排第一」→ 一致 ¥459 空气炸锅 ✅【生产实测】
- 「单笔最便宜」「每笔支出里最小」→ ¥36 地铁卡充值 ✅；「金额倒数第二」「第二便宜」→ ¥68 ✅
- 前提纠错：「我最贵的一笔支出是368.5元吗？」→ 直接给出 ¥459，未顺着编 ✅
- 台账合计：「本周餐饮台账合计是多少？」→ 454 元 ✅；全量合计 ¥1260 精确（台账只计一次）✅

**P1-1（新）：空格分隔的多行台账逃逸台账聚合判定，合计冒充单笔参与序数排名。**
- 现象：「支出第二高的是哪一笔？」→ 「你金额第 2 大的一笔支出是 ¥454…本周餐饮台账」（真值应为 ¥155 请客吃饭）；「按金额排，第二贵的东西」同样答 454；「餐饮台账里最贵的一项明细是什么？」→ 答台账合计 454 而非明细行 368.5。均为**确定性口径、肯定语气**的错误答案。【生产实测】
- 根因：`isLedgerAggregateNote`（ask.ts:485）依赖 `parseLedgerTable`，而 `splitCsvFields`（triage.ts:572）只认逗号/制表符/分号分隔；「早餐豆浆油条 12.5」这类**空格分隔**的台账每行只有 1 个字段，被判为非表格返回 null。与此同时 AI 分拣却读懂了「合计 454」并把 454 写入 note.amount——于是该笔记以 454 元"单笔支出"身份进入 finExtreme 的确定性排序（index.ts:3050 的过滤失效）。【源码审阅】
- 影响核心主线：是。R190 收口的「台账明细行口径统一」只对解析器认得的分隔符生效；空格分隔是手机上最自然的记法之一。ask-eval 117/117 全绿说明评估集缺少该形态。
- 建议：`parseLedgerCore` 增加空格分隔退化解析（行尾金额模式「.*\s+¥?\d+(\.\d{1,2})?元?$」且 ≥2 行命中即视作台账列），或最低成本方案——`isLedgerAggregateNote` 对多行笔记增加「行尾金额求和≈note.amount」的兜底判定，两者都不必改动分拣。

**P2-1（新）：不带财务词的序数问法整条路由落空。**「按价格从高到低排，第三名是什么？」→「没找到相关笔记」+ 敏感解锁提示（答案明明存在，提示还误导向敏感笔记）。根因：问句无「支出/花/买」等 FINANCE_WORD，finExtreme 不触发，落入通用检索又无关键词可召回。【生产实测】建议：极值/序数正则命中且用户库存在 amount 笔记时，即使缺财务词也应走确定性路线或至少不给敏感误导提示。

**P2-2（新）：财务关键词路由把问句残片当整词匹配，误报「没有找到记账记录」。**「台账里团建烧烤花了多少钱？」→ 关键词取成「台账里团建烧烤」整串 LIKE 匹配失败（正文实际含「团建烧烤 368.5」）；忠实性套题里「空气炸锅花了多少钱？什么牌子？」→ 关键词取成「空气炸锅什么牌子」同样落空（该笔记确在库且极值问法能召回）。fail-closed 未给错数，但两问都是高频自然问法，找回失败。【生产实测】建议：关键词提取后按分词/子串降级重试（先整串、再去疑问残片、再拆词），而不是一次 miss 即放弃。

## 5. 设计质疑：2 个未审过的流程深挖

### 5.1 备份→跨账号恢复闭环（数据可携与敏感闭包）✅ 设计自洽，1 条设计建议

质疑：备份的本义是灾备/搬家，脱敏默认会不会让用户「以为备份了，其实敏感笔记丢了」？生产实测全闭环（-bk1 → -bk2）：

- 默认备份：敏感笔记正文/标题=「[已加密内容]」占位，tags 清空、派生 meta 剥离，zip 全文无明文泄露（逐字节验证）；manifest 明示 `include_sensitive:false`。✅【生产实测】
- 敏感明文导出的二级防线：`?include_sensitive=true` 无密码复核头 → 403 password_required；带密码头 → 200 且明文在包内。token 泄露 ≠ 敏感明文拖走，分级合理。✅【生产实测 + 源码审阅】
- 跨账号恢复（搬家场景）：脱敏包恢复到新账号 → `sensitive_skipped:1` 显式上报、不产生占位壳笔记；UI 恢复文案明确提示「迁移敏感内容请用勾选敏感内容的完整备份」；文件名后缀 `-full` 区分两种包。恢复入库不信任包内 is_sensitive 定论，统一走持久层敏感管道（防篡改 zip 绕过）。✅【生产实测 + 源码审阅】
- 是否真的最适合？基本是——「默认脱敏 + 密码复核解锁全量」把常见误操作（备份文件随手传网盘）挡在默认路径外，代价（搬家需显式勾选）有 UI 文案与恢复统计双重兜底。**设计建议 D-1**：下载完成 toast 已注明「敏感内容已脱敏」，但建议在「下载完整备份」按钮旁常驻标注当前包是否含敏感内容（而非仅事后 toast），进一步压低「拿脱敏包当唯一灾备」的概率。不影响核心主线。

### 5.2 账号找回（一次性恢复码）与凭证轮换 ✅ 设计自洽，1 条设计建议

质疑：无邮箱/手机号的极简账号体系里，「用户名+一次性恢复码」是否足以支撑「可靠找回」的前提（账号丢=全部笔记丢）？生产实测：

- 恢复码重生成（登录态）→ 用错误码/不存在用户名找回 → 统一 401「用户名或恢复码错误」（防账号探测）；用正确码 → 200 返回新 token+新恢复码。✅【生产实测】
- 一次性消费确证：用过的码立即失效（replay → 401）；找回后旧 token 立即 401（全部 token 轮换，泄露 token 随旧密码陪葬）；限频按 IP+账号双键。✅【生产实测 + 源码审阅】
- 是否真的最适合？安全语义正确且实现干净（原子 batch 轮换）。**设计建议 D-2**：找回成功会静默杀掉所有旧 token——用户配置过的 MCP/浏览器扩展/Android 会同时掉线且无任何提示来源；建议找回响应与设置页明示「所有设备与集成需重新配置 token」。另外恢复码只在注册时展示一次，密码+恢复码双丢即永久锁死（无邮箱是产品选择，锁死语义应在注册页更醒目）。不影响核心主线。
