# R202 修改轮决策记录（落实 audit-r201）

对应审查报告：`docs/audit-r201.md`（R201 终定 GO，无 P0/P1；1 个沿袭 P2 + 4 个 P3）。本轮清 4 个 P3 + §1 修复建议，其余逐条评估。

## 1. §1 建议：SW 注册失败可观测与自愈 → 实施

R201 §1 结论：横幅是 `onRegisterError` 对真实失败态的正确呈现，属间歇性浏览器侧 sw.js 获取失败，非部署产物/MIME/CSP 缺陷；建议先拿到真实用户侧失败原因分布，并加自动重试。

实施（全部收口在既有 `ReloadPrompt` 失败态管道内，无平行状态管理）：

1. **错误上报**（`reportSwError`，`reload-prompt.tsx`）：`onRegisterError` 与每次重试失败时向 `POST /api/metrics/sw-error` 发送 `{name, message, retry}`——只含错误名称/消息（各截断 80/300 字符）与重试序号，不含任何用户内容、token 或 URL 参数；API base 取 `defaultApiBase()`（已保存值/构建时值/官方域名），未配置时静默跳过。上报用 `keepalive` fetch，失败静默，绝不影响页面。
2. **后端 beacon 端点**（`index.ts`，挂在 bearer 中间件之前）：注册失败的页面多半拿不到可用 token，故为公开端点；复用 `checkRateLimit`（同一 D1 限频器，`sw_error_report:<ip>`，5/分钟）防刷；只写结构化 `console.error` 日志（Workers 可观测性按 message 聚合失败原因分布），**不落库**、控制字符清洗、字段截断。如无必要勿增实体：不建表、不加 KV，日志管道即够回答「失败原因分布」这一问题。
3. **自动重试/退避**：注册失败后 30s → 60s → 120s 三档静默重试 `navigator.serviceWorker.register('/sw.js')`，成功即撤横幅；离线时该档不计数顺延。横幅文案改为「会自动重试，也可刷新重试」。重试上限 3 次：间歇性失败（审查判定的主因）一两次内即恢复，持续性故障重试再多也无用、只会打点噪音。

回归：`backend/test/r202-fixes.test.ts` 锁端点无需认证可上报、畸形 body 不报错、同 IP 超频 429；SW 失败态注入与自动重试恢复走生产 CDP 受控故障注入实测（QA 见 PR）。

## 2. P3-4 auth_rate_limits 滞留 → 存量已清 + 机制论证不加新实体

生产实查（2026-08-19，只读后再清理）：19 行滞留 key 全部 <24h（oldest `2026-08-19T08:19`），**无任何 >24h 的行**——既有两级机制在生产实际工作正常：

- **TTL/定期清理已存在**（R128）：`sweepAuthRateLimits` 每 10 分钟 cron 执行，保留期 24h（`RATE_LIMIT_RETENTION_HOURS`，保留短期是为排障事后取证）；若无此机制，历史 QA 轮（R192/193/195…）的 key 应累积数百行，实测只剩当天的 19 行。
- **注销清理已存在**（R140）：`deleteUserData` 级联删除 `%:<userId>` 与 `%:acct:<name>` 两类 key（LIKE 通配符已转义），有单测锁定（`account-cascade.test.ts`）。
- 审查所见 19 行的真实构成：对**不存在/已注销账号**的失败登录探测 key（`login:acct:[QA-R193]-nope…`，注销级联天然无从清理——账号从未存在）、纯 IP 维度 key（无法归属账号，本就留给 TTL）、审查自身 eval 账号的 key。这些正是 24h 保留期设计覆盖的场景，不是机制缺口。
- **存量已清**：`DELETE FROM auth_rate_limits WHERE key NOT LIKE '%u_boss%' AND key NOT LIKE '%:acct:Thomas'` 清掉全部 19 行（复查 COUNT=0，未触碰 u_boss 相关 key——实际也不存在）。

结论：不加新 TTL 字段/新 cron/访问路径惰性删除（请求路径加写放大无收益），机制已齐备且生产实证有效；本轮只做存量清理与论证。

## 3. P3-1 「是否为 X 块钱」变体 → 修复

R201 §2.1 实测：「最贵的一笔支出**是否为** 459 块钱」落 RAG 诚实但答非极值。根因：`EXTREME_PREMISE_RE` 的引导词捕获组是单选（是不是|是否|是|为），「是否**为**」「是否**是**」「是不是**为**」这类双动词变体第二个系词卡在数字前导致整体不匹配。

修复（`ask.ts`）：引导词捕获组后允许一个可选系词 `[是为]?`；配套把「否/为」加入 `EXTREME_FUNCTIONAL_RESIDUE_RE` 残渣字符集（「是否为」剥金额后的「否为」不是主题词；真主题如「华为手机」含实义字不受影响）。回归锁 R200 全部既有变体 + 序数/时间数字不误判。

## 4. P3-2 分拣金额按用量换算（25 元记 12.5）→ 修复

R201 实测：「咖啡机除垢剂 25 元，一次用半瓶」分拣 amount=12.5（按半瓶换算）。属 LLM 过度推断，与既有「AA 只有明确说了才取净额」同类：金额语义 = 实际支付的钱数。

修复（`triage.ts` prompt）：在 AA 判例前加显式规则「用量/份量/使用次数绝不改变支付金额」+ 三个判例（一次用半瓶→25、能用三个月→60、3 斤 90 元→90）。prompt 判例是该管道既定的修复手段（与 R195/R197 台账方向同路径）；不加输出侧后校验——「用量换算」无确定性识别特征，后校验会误伤真实单价类笔记。

## 5. P3-3 「本月最大收入」记录/事件时间口径 → 口径明示（沿袭 R199 P3-5 决策）

R201 实测：正文写「三月回款 4500」的笔记当日刚入库，「本月最大收入是 4500 元吗」答「本月没有已识别单笔收入」。经查这是**台账合计排除**与记录时间口径的叠加呈现——时间过滤按 `created_at`（记录时间）是全系统一贯口径（R199 P3-5 已决策明示而非改口径：改成解析正文事件时间会引入大量误判且与「碎念=随手记」心智冲突）。

实施（`ask.ts` `buildFinanceExtremeAnswer`）：极值问答带时间短语且零命中时，答案追加「时间范围按笔记记录时间划定，不按正文里写的时间」——与台账合计口径明示（R198 P3）同一话术，用户能看出口径差异而不是以为数据丢了。

## 6. P2-1 召回同义/量纲改写未命中 → 不改核心（论证）+ MCP 措辞小修

R201 定性「修一类又现一类，属长期改进面而非回归」（车厢号/几寸/植物/下个月安排 4 例，均诚实 no-answer 非幻觉）。逐例看：车厢号/几寸是量纲词形（12 号车厢 vs 几号车厢）、植物是上下位词（龟背竹→植物）、下个月安排是时间语义推理——不存在共同的确定性收口点，逐例打词表补丁正是审查点名的「修一类又现一类」模式；系统性方案（查询扩展/更强 embedding）是独立设计项，需按 SOP-02 先出样本与验证方式论证，不塞进 P3 清理轮。本轮维持诚实 fallback，留待专项。

例外小修：MCP `ask`/`search_notes` 的「剪藏」措辞未命中（R201 §5）有确定性收口点——`source` 参数描述补「extension（浏览器剪藏，用户说剪藏/收藏的网页文章时用这个）」，让 MCP 调用方模型能正确映射来源过滤。

## 7. 生产 QA 新发现：「本月最大收入是 4500 元吗」自相矛盾 → 修复

R202 生产 QA 实测：该问法返回「不是。本月最大收入是 4500 元」（自相矛盾）。根因：极值措辞正则要求「最大的一笔/一项」，「最大收入」这类极值词直接修饰财务名词的形态不匹配 → `financeExtremeIntent` 返回 null → 落 RAG 由 LLM 下是/否结论。

修复（`ask.ts`）：max/min 措辞正则各加 `最[大高小低]的?(收入|进账|入账|支出|消费|开销|花销|花费)` 分支（仍要求财务名词在场，「最高的山」不误收）；「最/来源」加入 `EXTREME_FUNCTIONAL_RESIDUE_RE` 残渣字符集防止「最大」漏进主题词 WHERE 自我否证。回归锁三例 + 歧义保护。
