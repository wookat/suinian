## 四、本轮新发现问题

1. **财务意图 fail-closed 过度触发（P2，可靠找回）**：「买的两本书叫什么，一共花了多少钱」是单笔事实查询（笔记原文写着「一共 96 元」，且已在召回引用第 8 位），却被当成「带限定条件的合计」拒绝心算、甩出全账本汇总。用户问书名+价格，得到的是月度收支表。建议：意图判定命中「限定条件合计」时，先检查召回集中是否存在单条笔记直接含答案（如金额与主题同句），有则直答。
2. **拒答建议列表两类失真（P2，可靠找回·信任感）**：
   - 主题笔记缺席：问「理发花了多少钱」，建议列表为 服务器续费/打车/豆浆油条，而真正的主题笔记「下午想去理发…剪艺在二楼」未入选——语义分数上「花钱类」笔记压过了「理发」主题笔记。
   - 零召回误称「找到了相关的笔记」：问「去上海的机票」（语料完全无关）也走 not_in_notes 口径，把 落地页/云南旅游 称作「相关的笔记」——R115 的口径失真反向出现。建议 mode 判定再加主题词命中校验。
3. **恢复 media_skipped 重复计数（P2，低频）**：重复恢复含 2 个媒体的备份，media_skipped 报 4——重复笔记的附件在笔记循环计一次（backup.ts L435），media/ 条目处理时因 idMap 无映射再计一次（L499/505）。计数翻倍，用户困惑。
4. **暗色模式洞察页横向滚动条为系统浅色样式**（P2，视觉，测试代理截图）——热力图下方滚动条与深色背景不协调。
5. **agg 类「吃的花销」漏水果（观察）**：答 58.7（早+午+晚餐）漏了引用里就有的水果 23.8——「吃的」口径由模型自由裁量，非确定性，暂不判级。

## 六、设计质疑与「可公开推广」差距（重点 5）

**每处设计反复问「是否真的最适合」后，本轮维持/新增的设计判断：**
- 敏感 fail-closed 的粒度（D1 第三轮出现，升级提请决策）：取件码、联系人电话这类「低危高频找回」信息被整条加密后，问答、待办、今日回顾全部不可见——张经理那条连「下周二回访」的安排都一起锁死。安全铁律（密码 0 泄漏）本轮再次全过 ✅，但代价日益明显。建议方向（不增实体优先）：分拣时把「凭据类」（密码/私钥）与「联系类/时效类」（电话/取件码）分开，后者默认不加密只打标；或至少让敏感 todo 的 due 提醒仍然生效。**需老板定口径。**
- 「事件/日志 vs 待办」分拣颗粒度：连续三轮（R107/R113/本轮）出现同型问题，说明 prompt 层面已到收益边界，建议下一修改轮给 triage 增加「完成式/事件叙述不是待办」的显式判据+少量 few-shot，并以 triage-eval 固化基线。
- 认可项：恢复幂等去重、fail-closed 财务、勿增实体的洞察范围实现（复用 /api/stats 一个 query 参数）——高内聚低耦合，✅ 认可。

**距「可公开推广」的必须项清单（按优先级）：**
1. **财务方向分拣加固**（本轮 P1）：交/付/缴+金额 → expense 的方向性校验（规则兜底+eval 用例），错账直接摧毁记账信任。
2. **财务 fail-closed 收窄**（§四-1）：单笔直答优先，避免「问书价得账本」。
3. **敏感分级口径**（D1）：老板拍板前至少把「敏感 todo 提醒失效」补上。
4. **拒答建议相关性**（§四-2）：主题词命中校验，宁缺毋滥。
5. **微信输入入口上线**：README 主打「微信随手发」，当前未上线——「什么都能丢」的获客承诺缺最大入口（营销侧受阻）。
非阻塞：暗色滚动条、media_skipped 计数、事件/待办颗粒度（迭代收敛）。
