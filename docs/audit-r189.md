### 2.3 聚类新阈值（floor 0.58 + top-3）精确/召回实测 ⚠️ P1-3

两份受控语料，均在显式 `POST /api/threads/rebuild` 后统计**成对（pairwise）**指标：

**语料 A**（`-cluster` 账号，22 条：晨跑/咖啡/装修/日语各 4 条 + 6 条噪声）

```
rebuild: {"status":"done","total":12,"summarized":2,"threads":2}
线索：咖啡制作技巧 4 条（4/4 全中）、晨跑 8 公里 3 条（3/4）
装修 0 条成线索、日语 0 条成线索、噪声 0 误聚
```

- 成对精确率 **100%**（9/9 对全部同主题，零误聚 —— 相比 R187「杂项误聚成拼凑线索」有改善）
- 成对召回率：按全语料真值 24 对计 **37.5%**；只按参与聚类的 idea 笔记真值 10 对计 90%
- 根因（【源码】`backend/src/threads.ts:29` `THREAD_CATEGORIES = "('idea','collect')"`）：装修组被分拣成 1 data + 1 idea + 2 todo，日语组 2 idea + 2 todo，**只有 idea/collect 进聚类池**，主题被分拣结果切碎后不足以成线索 —— 与 embedding 阈值无关（详见 6.1 设计深挖）

**语料 B**（`-pen` 账号，14 条全 idea 措辞：NAS 4 / 写作 4 / 睡眠 6）

```
rebuild: {"status":"done","total":14,"threads":1}
线索「遮光窗帘购买考虑」7 条 = 睡眠 6 条 + 写作 1 条（「写东西的节奏改成先写烂初稿」误入）
NAS 4 条（同一件事：老电脑改存储/RAID1/群晖/局域网访问）0 条成线索
写作 剩余 3 条 0 条成线索
```

- 成对精确率 **71.4%**（15/21，6 对为跨主题误聚）
- 成对召回率 **55.6%**（15/27）

**合计：精确 80.0%（24/30）、召回 47.1%（24/51）。** 对照 R187 实测（精确 81.8% / 召回 75%，语料不同不可直接比较），R188 把 floor 从 0.62 降到 0.58 后：本轮**没有观察到召回改善**，且出现了跨主题误聚。四个语义上明确的主题组（装修、日语、NAS、写作）**全部零线索**。线索是「AI 整理」承诺的串联价值，这是本轮该环节的主要扣分项。

## 6. 设计质疑：2 个未审过的流程深挖

### 6.1 线索聚类的「资格门槛」与「相似度阈值」耦合在一起，是否真的最适合？

现状【源码 + 实测】：

- 聚类池资格由分拣类别决定：`THREAD_CATEGORIES = ('idea','collect')`（`threads.ts:29`），todo/expense/data 笔记永不进线索
- 召回不足时，历轮的修法是**动阈值**：0.5 → 0.62（R178 精确率优先）→ 0.58 + top-3 确认（R188）

质疑：

1. **调错了旋钮。** 语料 A 的装修组（1 data + 1 idea + 2 todo）与日语组（2 idea + 2 todo）零线索，损失来自**资格过滤**，不是相似度不够 —— 阈值再降也救不回来。R188 的离线 A/B 只在 idea 语料上做，测量口径**先天看不到**这部分损失，于是连续两轮都在调阈值。
2. **两个正交的东西被耦合。** 「这条笔记是待办还是想法」（分拣，对象是行动属性）与「这几条笔记是不是同一件事」（串联，对象是主题）是两个维度。真实生活里一件事天然横跨类别：装修 = 想法 + 待办 + 报价数据。用分拣结果当聚类资格，等于让一个 LLM 判断去否决另一个维度的能力，且用户完全看不见这条规则。
3. **与产品承诺冲突。** 「什么都能丢 → AI 整理」隐含的是「同一件事会被串起来」。当用户丢的正好是「装修那摊事」的混合记录时，产品给出零线索 —— 这是承诺打折最直观的场景。

更好的方式（供 R190 论证，不替 R190 定案）：

- 把资格从「类别白名单」改成「信号门槛」（有实义内容/非零信号即可入池），类别只作为**排序/摘要口吻**的输入，而不是准入开闭；线索标题/摘要仍可只由 idea/collect 主导
- 精确率保护改用**结构信号**而不是继续压阈值：本轮误聚（写作笔记入睡眠线索）恰好说明纯 embedding 阈值在中文短句上分辨力有限；图谱实体/时间邻近/共现标签这类信号已有实现（`graph.ts`），把它们作为**必要条件之一**比调 0.58/0.62 更可解释
- 度量口径必须改：评估语料要含**跨类别主题组**，指标用成对精确/召回并同时报「零线索主题组数」——否则下一轮还会重复「调了阈值、指标看着好、生产没改善」

### 6.2 「问答确定性路线 = 一串正则意图识别 + 关键词主题提取」，是否真的最适合？

现状【源码】`backend/src/ask.ts`：财务聚合、财务比较、环比、列表、计数、极值、序数、枚举、元问题、指代、多跳……每类各有一套正则；极值路线还要靠 `EXTREME_STRIP_RES`（8 条正则串联）把问句「剥」成主题限定词注入 SQL。历轮每发现一个漏判就补一条正则（R148/R173/R174/R175/R178/R182 的注释就是这条演进史）。

本轮实测的代价（P1-1 的根因）：

| 问法 | 结果 |
| --- | --- |
| 最贵的一笔花销是什么？ | ✅ ¥459 买空气炸锅（确定性路线） |
| 花得最多的一笔是哪个？ | ✅ ¥459 |
| **单笔**最贵的一笔支出是多少钱？ | ❌ 被「多少钱 + 关键词」路线截走，答「按关键词『单笔最贵的一笔』精确匹配…没有找到记账记录」 |
| **单笔**最贵的一笔支出是多少钱？买的什么？ | ❌ 落 LLM，从台账明细行编出「368.5 元，餐饮」 |
| **单笔**最便宜的一笔支出是哪一笔？ | ❌ 「没找到相关笔记」 |
| 最便宜的一笔花销是什么？ | ✅ ¥36 |
| 支出第二高的是哪一笔？ | ✅ ¥155（第 2 名正确） |
| **按金额排**，第二贵的东西是什么？ | ❌ 主题词被剥成「按排」→「无法比较金额大小」 |

即：**8 种同义问法 5 通 3 挂**，挂的三种恰好是「单笔」「按金额排」这类最精确的表述。剥词器把功能词残渣（`单笔`、`按…排`）当成主题限定注入 WHERE，于是确定性路线**自己否证自己**（真值明明在库里），fail-closed 又要求「绝不退回全局极值」，用户拿到的是「没找到」。

质疑与建议：

1. **实体过多（违背「如无必要勿增实体」）。** 十几条意图正则 + 一套剥词正则，彼此的优先级只靠代码顺序表达；每轮新增一条正则都在扩大交叉面，本轮的 3 个失败全部是「正则之间的缝」，不是模型能力问题。
2. **方向建议：一次结构化查询规划（query plan）替代 N 条正则。** 用一次小模型调用把问题解析成 `{intent, direction, rank, topic_terms, time_range}` 的**结构化槽位**，再由现有确定性 SQL 执行 —— 模型只负责「填槽」不负责「算数」，确定性与可解释性完全保留，而同义问法的鲁棒性由模型而非正则承担。正则退化为**兜底**与离线校验基线。这与知识库里「规则只做 fail-closed 兜底、主判交模型 + 真实标签」的原则一致。
3. **无论方案如何，先补口径。** 主题限定词若在剥词后长度 ≤2 且不含名词性内容（如「单笔」「按排」），应视为**无主题限定**而不是注入 WHERE —— 这是一条能立刻消掉本轮 3 个失败的 fail-safe，且不引入新实体。
4. **必须消灭「静默错答」。** 「368.5 元，餐饮」是本轮最危险的一条：答案自信、有引用、数值来自台账明细行。确定性路线未命中而落 LLM 时，凡涉及金额比较/排名，应统一拒答或声明不确定，不允许 LLM 在台账明细上做极值推断。
