### P1

- **P1-1 `users.api_token` 明文存储**【D1 实查】：D1 users 表直查可见全部用户（含 u_boss）的完整 API token 明文。api_token 是全权凭证（API/MCP 共用），任何拿到 D1 读权限的人（误配的 CF token、备份泄露、内部误操作）即可完全接管所有账号。密码已哈希，token 却明文，口径不一致。建议与密码同口径：存哈希、比对时哈希查找（token 前缀可保留用于展示）。不影响核心主线功能，但属于「可公开推广」前应补的凭证卫生。

### P2

- **P2-1 分拣 tag 污染导致财务子集合计偏高**【生产实测】：AI 分拣把 2 条「燃气费缴纳」也打上 `水电费` tag，finance_subset 按「标题/正文/标签」匹配后「水电费一共交了多少钱」答 ¥750（真值 ¥600，多算 2 笔燃气费）。答案有逐笔明细可自查、口径也明示，故不算失实，但数字对不上会伤「可靠找回」信任。根因是分拣 tag 粒度（水电燃气混标）× 子集匹配含 tags。影响核心主线（找回准确性），建议：财务子集匹配对 tags 命中降权/单列，或分拣提示词区分水电/燃气。
- **P2-2 财务追问关键词抽取劣化**【生产实测】：带历史追问「包括打车费吗」被抽成关键词「你包括打车费内」，fail-closed 诚实拒算但答非所问（用户问的是"总数里含不含打车费"）。R149 同场景（q91「包括买跑鞋的钱吗」）能答"不包括"，说明能力存在但对措辞敏感。不阻塞主线（fail-closed 兜住了失实风险）。
- **P2-3 新账号语义搜索低相关命中**【生产实测，UX 走查】：仅 3 条笔记的新账号搜「跑步」，咖啡笔记也以「语义匹配」入列。小样本下 0.45 阈值偏松，新用户可能困惑搜索精度。建议小库（<N 条）时提高语义门槛或隐藏低分命中。

### 设计建议

- **D-1 移动端 FAB 轻微遮挡卡片操作区**（375px 下 + 按钮压住时间戳/⋯菜单角落，可点但局促）——UX 走查发现，建议 FAB 底部留白或滚动时收起。
- **D-2 恢复码页面无「我已保存」确认**——恢复码是找回唯一凭证（忘密码=丢全部数据），当前可直接点过，建议加确认勾选或下载按钮。
- **D-3（深挖 1）实体解析 O(N) 全表扫描**：`resolveEntity` 每个抽取实体都 `SELECT * FROM entities WHERE user_id=?` 全量拉取 + JS 内逐一 cosine。个人库千级实体内可行，但每条笔记 × 每个实体一次全扫，重载导入时是放大器。同时 `deleteNoteGraph` 的孤儿清理 `DELETE FROM entities WHERE note_count = 0` 未按 user_id 限定，跨用户删的是零引用垃圾行、数据上无害，但与并发中「刚 INSERT note_count=0、边还没建好」的实体存在竞态窗口（低概率丢新实体）。建议：孤儿清理限定 user_id + 排除 created_at 最近几分钟的行。
- **D-4（深挖 2）语义召回 4000 条向量硬顶**：`semanticRecall` D1 兜底路径最多分页扫 4000 条向量（MAX_VECTORS），超过后更老的笔记对语义搜索不可见——与注释「page through ALL」自相矛盾，且这是静默失明（无任何提示）。当前 u_boss 库远未到量级，不紧急；但「什么都能丢→可靠找回」承诺下这是一个已知悬崖，建议：达到阈值时启用 Vectorize（绑定已预留）或至少日志告警。

## 6. 设计质疑：2 个未审流程深挖（重点 5）

### 深挖 1：知识图谱抽取链路（`backend/src/graph.ts`，历轮未深挖）【源码走读 + D1 实查】

- 链路：笔记→LLM 抽取实体/关系（严格 JSON、类型白名单、置信度钳制）→实体解析（先名/别名精确、后同类型 bge-m3 向量 ≥0.92 合并）→mentions/关系边去重入库→note_count 重算→meta 标记防重抽。敏感笔记与向量库同口径拒入，编辑重抽先删旧证据。整体高内聚：抽取/解析/删除都收在 graph.ts 单文件，删除有单条+批量两版且语义一致，孤儿实体随手清——这是"该有的层都有"的正面案例。
- 「是否真的最适合？」两点质疑：① 实体解析每次全表扫 + JS cosine（D-3），规模放大器；② 孤儿清理 DELETE 未限定 user_id，正确性上只删垃圾行但存在并发竞态窗口（D-3）。均为规模/边界问题，当前量级不发作。
- D1 实查佐证：edges/entities 对 users 零孤儿、note_count 口径可由 edges 重算复核，生产数据与设计一致。

### 深挖 2：语义检索存储（`backend/src/semantic.ts`，历轮未深挖）【源码走读】

- 设计：D1 JSON 向量为 source of truth，Vectorize 绑定为可选镜像（未启用）；交互查询 8s 超时降级纯关键词、后台批量 30s；敏感转正/转敏都会同步删/建向量；cron 批量回填带时间预算，AI 不可用即停不空转。降级纪律和敏感边界执行得干净。
- 「有没有更好的方式？」：MAX_VECTORS=4000 硬顶是唯一的坑（D-4）——静默失明比慢更糟，与产品「可靠找回」承诺直接冲突；且注释与实现矛盾说明这是后来加的保护而非设计本意。建议触顶告警或启用 Vectorize，不必新增任何实体。
- 结论：两条链路总体符合高内聚低耦合，未发现需要立即整改的结构性缺陷；D-3/D-4 是规模悬崖的提前预警。
