## 2. 意图路由架构审查（代码级 + 实测）

### 2.1 代码级评估 `[源码]`

`backend/src/ask.ts` + `index.ts` 的 `/api/ask` 现有 6 个串联的正则意图闸门，按硬编码优先级顺序执行：

```
financeClarifyTerms → financeAggIntent → extremeQueryIntent → countQueryIntent
→ topicEnumIntent → enumListIntent(+timeRange) → 普通检索（关键词/语义/GraphRAG/多跳）
```

碎片化证据：

1. **互斥靠层层负向短路**：`countQueryIntent` 先排除 `FINANCE_WORD_RE` 再排除 `FACT_QUERY_RE`；`extremeQueryIntent` 排除财务词；`topicEnumIntent` 又排除极值与计数。每加一个意图，所有旧意图的负向条件都要复审——已是 O(n²) 维护形态。
2. **同一语义多处正则重复**："哪些"同时出现在 `FACT_QUERY_RE`（用于否决财务聚合）与 `TOPIC_ENUM_RES`（用于触发枚举）；"多少"同时在 `AGG_WORD_RE` 与 `COUNT_Q_RE` 系。同一 token 在不同闸门里语义相反，行为取决于闸门顺序而非语义本身。
3. **双通道判定**：每个意图都要对原问题和 `rewriteAskQuestion` 改写后的问题各判一次（`origFinanceIntent ?? financeAggIntent(recallQuestion)` 模式重复 4 处），改写引入的词可能翻转路由。
4. **fail-closed 分裂**：财务与计数各自有独立的 fail_closed 残差判定逻辑（`residual.length < 2`），规则不共享。

结论：**路由规则堆叠已成事实**。当前 6 闸门尚可运转（实测无假阳性，见 2.2），但按每轮加 1-2 个意图的速度，下一轮再加意图（如时间范围枚举、对比类）时负向条件组合将不可审计。建议方向（设计建议 D-1）：统一意图分类层（轻量 LLM 单次分类 + 现有正则做 fail-closed 兜底与参数抽取），而非继续加正则——符合"规则只做兜底"的公司判断原则。**本轮不实现，仅提出。**

### 2.2 误路由实测 20 问 `[生产实测]`

普通问题 10 问（不应进精确路由）：`我为什么膝盖不舒服 / 妈妈生日送什么好 / 置身事内讲了什么 / 我什么时候去医院复诊 / 英语学习用什么方法 / 可乐鸡翅怎么做更入味 / 杭州哪家茶馆不错 / 咖啡豆推荐哪种 / 季度报告要发给谁 / 跑步之后膝盖疼怎么办` → **10/10 无任何精确路由 flag，零假阳性**。

精确问题 10 问（应进精确路由）：

| 问题 | 期望 | 实际 |
|---|---|---|
| 我一共花了多少钱 | finance | finance_aggregate ✓ |
| 打车和吃饭一共花了多少 | finance(条件) | finance_fail_closed ✓（正确拒绝） |
| 我总共记了多少条笔记 | count | count_aggregate ✓ |
| 我记了几条待办 | count | count_aggregate ✓ |
| 最早的一条笔记是什么 | extreme | extreme_aggregate ✓ |
| 最长的一条笔记是哪条 | extreme | extreme_aggregate ✓ |
| 我平均每天记几条笔记 | count | count_aggregate ✓ |
| 出差垫付了多少钱 | finance | **漏路由**：走普通语义检索 |
| 我都存过哪些菜谱 | enum | enum_aggregate ✓ |
| 最新的一条笔记是什么 | extreme | extreme_aggregate ✓ |

结论：假阳性 0/10（好），漏路由 1/10（"垫付"不在 `FINANCE_WORD_RE` 词表——词表式路由的固有天花板，每个新表述都要补词）。加上 1.1 的 7 问同义枚举漏路由，**漏路由（召回不足）是当前主要风险面，假阳性已控制住**。

## 5. 设计质疑：两个未审流程深挖

### D-A 批量导入后的异步整理流程（导入 → 分拣 → 嵌入 → 线索回填）

现状（[源码] `index.ts` scheduled cron + [生产实测]）：整理靠每 10 分钟 cron 的多个小批量任务（retriage 25 条/次、embed 20 条/次、`BACKFILL_BATCH=10`）串行消化，550 条导入需数小时才收敛，期间时间流满屏"分拣延迟"警告，且最终仍有 9 条永久卡在待分拣、199 条不入线索即宣告 `done`。

质疑："什么都能丢"承诺的是丢完就不用管，但大批量丢入后系统进入长时间半整理状态，用户既看不到进度也看不到终点，"done"的定义（回填游标走完）与用户期望（都整理好了）不一致。是否真的最适合？更好的方式：导入触发专用整理 job（复用 thread_jobs 的 slice 机制而非等 cron）、给用户暴露"整理中 x/550"进度、`done` 前对残留未分拣笔记做终态处理（归入待分拣收件箱并显式告知，而非无限"将自动重试"）。

### D-B bridge 无人值守生存流程（登录态维护 → 崩溃恢复 → 告警）

现状（[VPS 实查]）：登录态一旦过期，系统唯一行为是刷新二维码等人扫；扫码窗口无人在场时进程反复 crash（status=1）由 systemd 无脑拉起，形成"服务活着、功能死了"的假活状态，且这一状态可以无限期持续而无人知晓（本次审查发现时已持续多日）。

质疑：把一个依赖人工扫码的有状态登录，部署成无人值守 daemon，却没有任何"我需要人"的上报通道——这是流程设计缺失而非代码 bug。更好的方式：登录失效时通过已有可靠通道（如后端 API 打点 + Web 设置页红点，或 push_subscriptions 推送）通知 boss 扫码；连续 N 次登录失败后退避停机而非每 8 分钟崩溃重启；`/health` 应反映"已登录且可转发"而非进程存活。

## 发现分级汇总

### P0
1. **微信 bridge 实际瘫痪且静默**：服务假活、登录失效多日无告警，微信入口的"什么都能丢"承诺中断。**直接影响核心主线**（丢的环节）。`[VPS 实查]`

### P1
2. **大语料 36% 笔记不入线索 + 混簇/碎片化**（纯度 0.858 但最差簇 0.40；烹饪拆 7 簇；330 条全归"想法"）：影响"AI 整理"环节的可信度。`[D1 实查]`
3. **枚举/财务路由漏召回**：同义问法（列一下/清单/都有什么）7/15 不进精确路由；"垫付"类财务表述漏路由——词表式路由天花板。影响"可靠找回"。`[生产实测]`
4. **枚举话题词语义误召回**：`LIKE %书%` 把"读过的书"混入"买过的书"、正文含"地方"的读书笔记混入"去过的地方"，动词语义丢失。`[生产实测]`

### P2
5. 路由规则堆叠/意图判定碎片化（O(n²) 负向条件、同 token 跨闸门语义冲突、原问题+改写双通道判定重复 4 处）：当前实测行为正确，但可维护性临界。`[源码]`
6. 导入后异步整理无进度可见、9 条永久"分拣延迟"、`done` 语义与用户期望不符。`[生产实测][D1 实查]`
7. 枚举结果 31-50 条平铺列表含重复条目、线索页 38 项无同名去重/搜索，规模化可读性下降。`[生产实测]`
8. 近义标签并存（运动/训练、书籍/书摘）无归并机制。`[D1 实查]`
9. `skill/README.md`"自动重连"表述与实际（需人工扫码）不符。`[VPS 实查][源码]`

### 设计建议（不属缺陷，供决策）
- **D-1 统一意图分类器**：以轻量 LLM 单次意图分类替代继续堆正则，现有正则降级为 fail-closed 兜底与参数抽取。理由见 §2.1。建议先离线用本轮 35 问 + 历轮问题集做分类器对照实验再决定，勿直接改生产路由。
- **D-2 导入触发式整理 job + 进度暴露**（见 D-A）。
- **D-3 bridge 告警通路 + 有意义的 health 语义**（见 D-B）。
- **D-4 线索治理**：同名线索合并、主题碎片定期归并（sweepRecentDuplicateThreads 已有雏形但只处理 recent）。

### 与核心主线关系
- 丢：P0-1 直接中断微信通道；Web/导入通道健康。
- 整理：P1-2、P2-6/8 使大语料下"AI 整理"从"可信"降级为"大体可用但需人工复核"。
- 找回：P1-3/4 使精确找回覆盖面不完整，但零编造、零假阳性守住了底线。
