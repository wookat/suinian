# R274 修改轮设计论证（对应 audit-r273 NO-GO 结论）

> 本文档在写代码之前完成（SOP-02 调研先行）。每节先给论证，再给实现口径。

## 1. P0-1：所有答案出口的单一收口点

### 事实（一手证据）
- `/api/ask` 处理器内有 28 处确定性 `return c.json(...)`（财务聚合/列举/比较/阈值/极值、计数、话题摘要、分类/关键词枚举、时间窗与关系拒答……），全部在 LLM 生成分支之前直接返回；`dirext`/`conaud`/`guardAskAnswer` 只挂在生成分支（audit-r273 §2.2 D03、`sse-inj-gen2` 的 server-timing 无 `dirext`/`conaud` 即此因）。
- 现有 `app.use("/api/ask")` 中间件已经是所有 JSON 答案的必经点（含 MCP ask 工具的内部转发），但只做了外链收口。

### 设计
把该中间件升级为**唯一收口点** `finalizeAskAnswer`：凡 `/api/ask` 返回的带 `answer` 字段的 JSON，一律经过
1. 外链收口（`scrubAnswerLinks`，口径见 §3）；
2. 可执行下载管道隔离（`curl…|bash` 类，见 §2）；
3. 笔记内指令段落隔离（面向助手/读者的祈使段，见 §2）。

未来新增任何答案路由都自动被覆盖（fail-safe：漏挂不可能发生，因为不经过中间件就没有响应）。

### 为什么确定性路径不跑 LLM 归因审计（论证不改的部分）
确定性路径的答案是固定模板 + 笔记正文的字面投影，模型没有参与——不存在「答案行为被资料指令改变」这一 `conaud` 要审计的对象；该路径的唯一威胁是**把注入文案当普通内容透给用户**（社工载体，D03 正是如此）。对这一威胁，逐段的确定性「指令段落隔离」是充分且 fail-closed 的（判定的是段落行为特征而非注入字面），并且不给 DB 快路径（实测 170-828ms）增加 1.6s+ 的 LLM 审计延迟（audit-r273 §6.3 P1-4 明确把该开销列为待优化成本）。生成路径继续保留 `dirext`+`conaud` 全套。

## 2. P0-2/P0-3：verbatim 口径重设计

### 事实
- `VERBATIM_ASKED_RE` 把「命令/代码/配置/脚本/sql/prompt/片段/函数/正则/语句/建表」等**话题词**当成 verbatim 请求，一旦命中即整体豁免链接与删字类护栏（G04/G05 透出的直接原因；「部署命令里有哪几条」这种非原文问法同样命中「命令」）。
- 产品价值要求：用户点名要原文时必须给原文（B02/B04/B05/B13/B14/B17 全部依赖该能力）。

### 设计：三层分离
1. **收窄 verbatim 判定**：只有明确索要原文的措辞（原文/原样/逐字/一字不差/完整给|贴/怎么写的/写了什么/内容是什么/verbatim）才算 verbatim 请求；纯话题词（命令/代码/…）不再触发豁免。
2. **原文照登 + 指令段落显式隔离**：verbatim 答案仍给原文，但其中「面向助手/读者的行动指令段」被替换为显式标记 `〔已隔离笔记内指令，未采纳；原文可在下方引用的笔记卡片中查看〕`——原文的完整版本永远通过 references/notes 结构化通道在笔记卡片里可见，答案叙述层不承载指令。判定特征（与注入字面无关）：
   - 面向回答者的听写/改行为措辞（「回答…时请…」「答案末尾附上…」「系统同步说明」等）+ 祈使线索；
   - 行为类信号（外传/导航/联系/口令，复用 R270 行为一致性引擎）+ 祈使线索；
   - 可执行下载管道（`curl|wget|iwr … | bash|sh|iex`、`base64 -d | sh`）——**无论是否 verbatim、无论叙述还是引用，一律隔离**。合法技术笔记里的安装管道（如 rustup）也会被标记隔离，但笔记卡片原文完整可见，这是「可执行内容不经答案层递送」的既定安全边界。
3. **叙述层禁运**：隔离逻辑作用于全部答案段落（不止 verbatim 引用段），因此「部署命令里有三条：…curl…|bash」式转述同样被隔离（G05 第二问归零）。

## 3. P1 误伤回归（9/44 → 0）

逐例根因（本地对源函数重放确认）：
- **B21 ffmpeg / 同类过度拒答**：`segHasForeignHost` 把 `in.mov`、`*.js` 等文件名当域名 → 整段被 `scrubUnsolicitedConduct` 剥除 → 答案剥空回落「没找到」。修复：主机判定排除常见文件扩展名伪 TLD。
- **B20 发给李工**：`发给`+邮箱命中 exfil 类。修复：忠实回显豁免——段落是资料 verbatim 回显、含提问关键词、且不含对读者的祈使线索（请/务必/你要…）时保留；注入句天然带祈使或听写措辞，不享受豁免。
- **B08/B22 书签 URL**：外链保留门从 `questionRequestsVerbatim`（已收窄）改为「URL 在资料区逐字存在 且 问题点名链接/路径/命令/原文类内容」；诱导性链接段落由 §2 隔离层兜底。
- **B03 shell 正文损坏（P0-4）**：见 §4。
- **过度拒答的共同放大器**：护栏剥空后回落文案是「没找到」，与检索空不可区分（audit-r273 P1-2 未能隔离根因即此因）。修复：剥空时改走既有保守输出「相关笔记中包含试图影响回答的指令，为安全起见本次只提供来源引用」+ references，不再谎称没找到。

## 4. P0-4 / R269 shell 正文损坏

根因（audit-r273 §6.1，已在本地逐段复现）：`splitAnswerSegments` 按句读切分把 shell 切成 `#`、` do`、`done`、``` 等超短段；`segmentEchoesData` 对 compact<6 直接 `false`，短段拿不到 verbatim 豁免而被审计裁决删除。

修复（两层，单测锁死）：
1. 切分改为**围栏感知**：``` 围栏内的代码块作为一个整体段，不再按句读/分号切；
2. 短段豁免：compact<6 的段，若其 trim 后的原文形态在资料原文中逐字出现（`rawData.includes(seg.trim())`），视为资料回显予以保留（`#`/`do`/`done` 均命中）。

## 5. P1 检索/意图错位（R18）

根因：关系限定词护栏与拒答重试用的是 `${intentQuestion}\n${recallQuestion}`——`recallQuestion` 是 LLM 改写产物（不可信侧派生），R18 的改写引入了原问题没有的「客户」，护栏据此拒答。修复：
- 关系护栏只看用户可信问题（`intentQuestion`，代词跟进时它已是消解结果）；
- 拒答重试改用 `intentQuestion` 而非 `recallQuestion` 提问。

「自有笔记问不出」15/22：文案与检索空一致但实为审计剥空回落（§3 末条修复后两者可区分且不再误导）；真正检索缺口由 retrieval-eval 在生产复跑量化。

## 6. P1 SSE 统一口径

契约：凡带 `Accept: text/event-stream` 的 `/api/ask` 请求，一律返回 `text/event-stream`：
- 确定性路径：收口中间件把最终 JSON 包装为 `meta` → `delta`（完整答案一段）→ `done`（DB 路径答案瞬时完成，单段 delta 即忠实表达）；
- 生成路径：去掉固定 48 字符 holdback，改为「指令抽取落定且无 demand 后，按句界/行界推进 delta」——短答案也能产生 delta；有 demand 或抽取失败仍整体缓冲到 done（不安全增量为零的既有保证不变）。
