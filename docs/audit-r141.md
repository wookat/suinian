## 一、R140 复核（重点 1）

### 1.1 敏感数字变体对抗 20 例（生产实测 ✅）
- QA 账号 `[QA-R141]-main`，新构造 20 例应敏感变体（空格分组、连字符、全角数字、混合分隔、+86 手机、身份证分段、中文数字混排、边缘格式）+ 3 例良性对照，逐条 `POST /api/notes` 写入生产。
- 判定方式：等待异步分拣完成后拉取终态 `is_sensitive`（创建即时响应不作数）。
- 结果：**20/20 应敏感样本终态 is_sensitive=true**；3 例良性对照未误伤。
- 细节观察：纯正则路径（`normalizeDigitRuns`：全角折半角 + 数字分组分隔符折叠，triage.ts）覆盖空格/连字符/全角/分段类；「中文数字混排」类个别样本即时响应未标敏感、由异步 AI 分拣兜底后标敏感——正则不识中文数字属预期，双层防线成立，但存在敏感内容明文短暂可见的窗口（与历轮已知的异步分拣窗口同源，不另立缺陷）。
- 判定：R140 敏感数字归一化修复在对抗样本下成立。

### 1.2 每日回顾 7 天冷却（生产实测 ✅，R140 上线后首次线上验证）
- QA 账号 `[QA-R141]-review`：造 3 条回溯日期的非敏感旧笔记，反复调 `GET /api/review/today`，并通过 D1 将 `daily_reviews.review_date` 逐日回移模拟多天：
  - 连续 3 个模拟日各选出 1 条**互不重复**的笔记；
  - 3 条均进入 7 天冷却窗口后，回顾返回空（不复读）；
  - 将记录回移 >7 天后，笔记恢复可选。
- 判定：`review.ts` 中 relaxedCandidates / recurringThemeCandidate 的 `review_date >= date('now','-7 days')` 排除子句生产真实生效，R139 发现的复读问题闭环。

## 二、导入迁移旅程复审（重点 3）

### 2.1 一键导入成功率（生产实测 ✅）
- 构造两家真实结构导出包：flomo HTML（15 条，含时间戳/内联 #标签/图片引用）、Cubox CSV（10 条，含标题/描述/URL/标签/文件夹/历史时间）。
- 结果：flomo **15/15**、Cubox **10/10** 导入成功；创建时间、标签、来源、URL 全部保留；0 失败 0 跳过。
- 重复导入防护（同时间+同内容去重）与 20MB 上限提示与文档一致。

### 2.2 导入后分拣/聚类/问答质量
- 分拣：25 条导入笔记**全部**完成 AI 分类（idea 11 / collect 10 / data 4 / todo 2），无漏分。
- 聚类：全量重建（job done，21 条处理）后仅形成 **1 条线索（2 条笔记）**。语料含读书、健身、产品想法、菜谱等多主题、各主题 2–4 条，聚类覆盖率 2/21≈10%。→ P2-1。
- 问答：主题枚举「flomo 里记过哪些读书笔记」召回 6 条（含 2 条弱相关，关键词式筛选精度一般但如实声明了口径）；「健身相关」精确召回 2 条并带引用；「效率工具文章」召回正确。找回能力整体成立。

### 2.3 flomo 图片资产（设计缺口，已文档化）
- flomo 官方导出是 zip（index.html + file/ 图片目录）。生产实测：`POST /api/import?source=flomo` 上传 zip 被拒（「该来源不支持 zip」），必须手工解压取 HTML；且设置页明确提示「flomo 压缩包里的图片暂不导入」。
- Notion/Obsidian/Apple 备忘录已有完整 zip+图片入库管线（import-zip.ts）。flomo 未复用该管线导致：迁移用户图片全部丢失 + 多一步手工解压。→ 设计建议 D-1。

## 五、设计质疑：2 个未审流程深挖（重点 5）

### D-A 回收站/软删除生命周期（`purgeExpiredSoftDeletes` / trash 路由，历轮未深挖）
- 机制：软删标记 `deleted_at`（30 天保留，客户端可见 purge_at）→ cron 批量硬删（200/批 + 20s 时间预算，跨多轮清积压）→ 硬删时同步清 attachments+R2 原件、嵌入、图谱行、daily_reviews，并 reconcileThreads。检索/问答/回顾/报表/推送共 14 个模块逐一带 `deleted_at IS NULL` 过滤（全库核对）。
- 质疑 1：**排除靠"每条查询自觉带过滤"而非结构隔离**。14 处手写 `deleted_at IS NULL`，新增查询漏写即泄漏已删内容。是否最适合？替代：视图（notes_live）或查询构造器统一注入。现规模尚可，属可接受债务，建议在下一次 schema 变更时顺手收敛。
- 质疑 2：软删期间嵌入与图谱行**保留**（仅硬删时清）。语义检索在 semantic.ts 侧有 deleted_at 过滤，行为正确；代价是已删内容的向量与实体在库中滞留最长 30 天。对单用户产品可接受，但「彻底删除」的用户预期是否包含派生数据即时消失值得一提——当前"彻底删除/清空回收站"走 purgeNotesBatch 是即时清的，仅"等 30 天自动过期"路径存在滞留，语义自洽。
- 生产实证：见 §3 Web 回归（删除→最近删除含保留期→恢复→彻底删除→搜索/ask 不再召回）。

### D-B 待办提醒链路（`sweepTodoReminders`，历轮未深挖）
- 机制：分拣阶段 LLM 抽取 todo_due（正则判例防"外部事件当待办"，`demoteEventLog` 二次降级）→ cron 扫 ±2 天窗口 + 24h lookback → 用户时区换算提醒点（定时待办提前 30 分钟、纯日期 08:00）→ **先标记 todo_reminded_at 再投递**（at-most-once）；无订阅通道则不消耗提醒（等订阅后 24h 内仍可触发）；敏感待办推送脱敏为「一条待办」。
- 好设计：时区正确性、退避语义、敏感脱敏、偏好关闭时显式消耗，皆有单测判例支撑。
- 质疑 1：**at-most-once 取向**——先标记后投递意味着推送服务瞬时故障会永久丢失该次提醒（换取零重复）。对"待办提醒"这一场景，漏提醒的代价大于重复提醒；是否最适合？建议投递失败时回滚标记或加一次性补投（幂等键已有 tag=todo-{id} 可去重）。
- 质疑 2：提醒**只有 Web Push 一条通道**，无站内兜底。用户未授权浏览器通知（移动端 PWA 授权率低）则整个 todo_due 抽取链路的提醒价值为零，仅剩待办页手动查看。建议站内（时间线顶部/待办角标）作为零成本兜底通道。
