## 八、分级问题清单

### P2-1 `退货` 与 `退款` 词形不对称，`咖啡 19 退款/退货 -25(洒了)` 分拣不稳

- 证据（生产实测，`qa-r233/p21b-results.json`）：
  - `咖啡 19 退款 -25(洒了)` ×5 → `income 6` ×3、**分拣未完成（无 category/amount）×2**
  - `咖啡 19 退货 -25(洒了)` → **`idea`，无金额**
  - 同结构其它品类均正确：`奶茶 16 退款 -20(做错了)`→`income 4`、`水果 33 退货 -50(坏了)`→`income 17`、`零食 8 退款 -30(质量差)`→`income 22`
- 判定：R232 的 few-shot 回流对"退货/退款净收"结构总体生效，但**"咖啡"这一高频词条在退款语境下会被误判为想法/收藏**，且同一句多次复跑结果不一致（模型侧不确定性）。属"收"环节口径缺口，用户可见后果是该笔不进账本（无金额），不是金额错记。
- 建议（不在本轮实施）：把 `咖啡/奶茶` 等饮品 + `退款/退货 -X` 组合补进 few-shot；或在确定性台账解析里放宽"单品名 + 数字 + 退款/退货 + 负数"的匹配，不依赖模型判类。

### P2-2 结余禁推算未覆盖"乘法算式"形态

- 证据（生产实测，`qa-r233/p31-results.json`）：问 `游泳卡还剩几次，还有多少钱`，答「…每次游泳花费 60 [2]，游泳去了两次 [2]，所以花费了 **60 * 2 = 120**」。笔记中不存在 120 这个数字。
- 源码检查：`ANSWER_AMOUNT_RE` 的算式分支以"还剩/剩余/余额/结余 … `=` 数字"为前提，且其余分支要求货币符号或货币单位；`60 * 2 = 120` 三者都不满足，故未被剥除。
- 判定：R232b 修好的是"结余算式"这一形态，同一类"答案里自行做算术"的风险仍存在于乘法/加法合计形态。此例未给出余额（未答"还剩多少钱"），危害低于 R231 的余额幻觉，故定 P2 下沿。
- 建议：在答案后处理阶段，凡出现 `数字 [*x×+\-] 数字 *[=＝] 数字` 的算式一律剥除并改为"不做心算合计"话术，与既有精确 SQL 合计通道统一。

### P3-1 敏感笔记明文在本人已认证接口可见（设计确认项，非缺陷）

- 证据（生产实测）：本人 token 调 `/api/notes`、`/api/notes?q=WiFi` 会返回敏感笔记明文正文。
- 判定：与既有设计一致（静态加密存储 + 界面侧遮罩 + 本人解锁可见；导出/问答/备份/MCP 均已隔离）。列入清单仅作**边界确认**，不建议改动；如未来要收紧，应是"列表默认返回遮罩、详情按需解密"，属产品决策而非安全缺陷。

### P3-2 "代收后转付"句式判为 `transfer` 而非 `income`

- 证据（生产实测，`qa-r233/drift-results.json`）：`帮邻居代收的学费 300 已经转给老师了` → `transfer 300`（期望 `income 300` 或"净额 0 的代收"）。
- 说明：该句是本轮新造变体；R223 历史固定判例 `学生给我交了补课费 300`（本轮**未复跑**，标注未验证）在提示词/eval/单测三处仍固定为 `income`。
- 建议：明确"代收代付"的产品口径（净额 0 更贴近事实），再决定是否加判例——直接改判 `income` 会让"钱已转给老师"的事实失真。

### P3-3 关键词切分导致 2 例召回未命中

- 证据（生产实测，`qa-r233/faith-results.json` #2/#17）：`杭州住宿订的哪里，花了多少钱` → 切成「杭州住宿订、哪里」未命中"杭州西湖边的民宿"；`信用卡还了多少钱` → 切成「信卡还」未命中"信用卡账单还了 4200"。
- 判定：均如实拒答未编造（幻觉 0），属召回质量问题。`信卡还` 这种切法明显是分词把"信用卡"与"还"拆错，建议优先修分词/同义扩展（信用卡账单/还款；住宿/民宿/酒店）。

### P3-4 卡类"充值"计入支出，导致合计口径易被误读

- 证据（生产实测）：`剪头发花了多少钱` → 「共 2 笔支出 ¥545」明细含 `剪头发的卡充了 500`；`游泳一共花了多少钱` → ¥920 含 `游泳卡充值 800`。
- 判定：口径可自证（明细逐笔列出），但"充值"与"消费"混入同一支出合计，对储值卡场景语义不准。建议给储值/充值单独归类或在合计话术里区分"充值 X + 实际消费 Y"。
