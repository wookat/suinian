## P1-1 q08「最近一周我花了哪些钱」12/12 全败：归因为检索候选遗漏，并伴随待办→支出幻觉（可靠找回）

【生产实测】独立账号重建 ask-eval 47 条夹具（golden 时间戳对齐：exp1=8 天前、exp2=5 天前、nz20=30 天前），
生产复跑 12 次（GraphRAG 开 10 次 + 关 2 次）：

- **12/12 未召回 exp2（窗内支出「猫打疫苗 260 块」），全部走 `llm_route`**；
- 引用集合始终是 `nz16`、`nz20` 等**窗外**笔记，回答「最近一周没有记录任何支出」；
- 关闭 GraphRAG 后更糟：run11/12 引用 `todo1`（"待办：本周三前交房租"）回答
  **「最近一周你花了房租的钱」——把未发生的待办当成已发生的支出，这是幻觉**；
- 直接调 `/api/search?q=最近一周我花了哪些钱`：命中 nz20/todo1/fit1/cafe3/exp1（全部 semantic），exp2 不在其中。

归因（按层排除）：

1. **时间窗解析正确**【源码+实测】：`ask.ts` 的 `最近一周` → 上海时区今日零点 -7 天，exp2（5 天前）在窗内；
   回答里也复述了正确的窗口边界。
2. **排序无关**：候选里根本没有 exp2，不是排序把它挤掉。
3. **根因在检索候选层**【生产实测支持】：这类问法先抽关键词做 LIKE 召回、再语义召回后按时间窗过滤；
   「花了哪些钱」抽出的关键词与「猫打疫苗」「机械键盘」字面零重叠，LIKE 空手而归；语义召回把
   「买跑鞋 549 元」（nz20，字面最像"花钱"）排前，exp2 相似度不足没进 top-N；窗内候选为空后，
   模型基于窗外候选自由发挥。（关键词抽取的确切词表未直接观测，属源码支持的机制推断。）

**修复建议（留给修改轮）**：「时间窗 + 财务列举」问法（哪些钱/花了什么/买了什么）不应依赖相似度召回——
账本类数据有确定性口径：识别到 finance 意图 + 时间窗后，直接
`SELECT ... WHERE category IN ('expense','income') AND created_at 在窗内` 列出明细，LLM 只负责措辞
（与 R168 财务比较类并入 `financeStats` 的思路一致，把"列举"也并进确定性路径）。同时无窗内候选时应
fail-closed 回答「窗内没有可引用的记录」，禁止引用窗外笔记或待办来"推测"支出。

## P1-2 多行 CSV 记账内容分拣永久卡死：22 分钟不分拣，1 小时后降级成「想法」（AI 整理）

【生产实测】安卓端经系统分享（Files → share sheet → 碎念）存入 3 行记账 CSV
（`日期,内容,金额 / 买咖啡豆 88 / 地铁充值 50 / 买绿萝盆栽 25`）：

- 文件接收、文本提取全部成功（`meta.file_status=ok`，正文即 CSV 全文）；
- 但笔记 `category` 22 分钟后仍为 NULL（UI 显示「分拣中」），经过多次 GET /api/notes 的机会式
  retriage kick 和至少一次 10 分钟 cron 清扫仍未恢复；
- **对照实验**：同账号同时段（a）普通支出笔记 45 秒内分拣成 expense/金额 180/标签；（b）把**同样的
  CSV 三行文本**作为纯文本笔记写入 → 同样永久卡在 NULL。故排除"AI 链路当时整体故障"，
  是**内容相关的确定性分拣失败**；
- 【源码】`retriageOne` 失败后 1 小时（`TRIAGE_DEGRADE_AFTER_MS`）才降级，且降级类别是
  `FALLBACK_TRIAGE.category = "idea"`——三笔支出最终会被打成一条「想法」，金额永不入账，
  财务统计/周报口径从此少记。

根因推断【源码支持，未直接观测模型输出】：多行多笔记账内容会诱导分拣 LLM 返回**多个 JSON 对象或数组**
（每行一笔），而 `parseTriageJson` 用 `indexOf("{")..lastIndexOf("}")` 切片，对 `{...},{...},{...}`
解析必然失败返回 null → 无限重分拣 → 每次同样失败。

**修复建议**：① `parseTriageJson` 对数组输出取第一个合法对象（或在 prompt 中强约束单对象输出并加
`response_format: json_object`）；② 结构化表格内容（提取自 csv/xlsx 的文件笔记）分拣时走"资料"快路径
或按行拆分成多笔支出（见设计建议 S-2）；③ 降级兜底从 1 小时收紧，且文件笔记降级类别用 `data` 而非 `idea`。

证据：`docs/assets/r169-and-csv-pending.png`（同屏可见：CSV 笔记「分拣中」，其下探针支出笔记已分拣出
「支出 -¥180」）、`docs/assets/r169-and-share-confirm.png`（系统分享确认页）。

## P2 列表

### P2-1 Big5 CSV 解码成乱码（什么都能丢：入库即损毁）

【生产实测】Big5 编码 CSV 上传 → 201，提取文本 `ら戳,兜ヘ,肂…`（乱码），检索与 AI 摘要基于乱码。
【源码】`decodeTextBytes` 链：UTF-16 BOM → UTF-8(fatal) → GBK 兜底；Big5 字节流落进 GBK 分支
"成功"解出乱码，无失败信号。R168 只修了 GBK。建议：GBK 解码后做常用字命中率启发式校验，
低于阈值再试 big5（Workers TextDecoder 支持），仍失败则存档原件并明示提取失败（现有 fail-safe 路径）。

### P2-2 PNG 伪装 .csv 被当文本收下（什么都能丢：轻微）

【生产实测】PNG 字节 + `.csv` 扩展名上传 → 201，正文是 `塒NG…IHDR…` 二进制垃圾。
【源码】`sniffFileKind` 只认 PDF/zip magic；非 zip 二进制落到扩展名判定被当 csv 文本解码。
建议：文本类扩展名在解码前检查 NUL 字节/不可打印字符比例，超标走"存档原件+提取失败"路径。
（对照：csv 伪装 .xlsx → 解压失败 → 正确存档原件不丢件【生产实测】，该路径行为合理；
若想更进一步可在 zip 解压失败后回退文本解码，属锦上添花。）

### P2-3 Android 语音转写失败一次（什么都能丢：轻微，fail-safe 生效）

【生产实测】安卓录音入口权限、录制、上传全部正常，停止后笔记正文为「转写失败，稍后可重发」，
音频文件保留且有重试入口（`retry-media`）。单次观测（同时段图片描述、文件提取正常），无法断定
转写链路持续故障，但按核心主线"语音丢进去要能找回"，转写失败率值得加监控。
证据：`docs/assets/r169-and-voice-fail.png`。

## 设计深挖一：线索聚类/重建——贪心近邻 + 固定阈值是否真的最适合？

【源码】`threads.ts`：新笔记对最近 200 条 idea/collect 做余弦，≥0.76 直接并线，0.62~0.76 让 LLM 确认；
重建 = 逐条重跑同一增量逻辑；同标题线索折叠合并。

**是否真的最适合？** 生产实测暴露三个结构性问题：

1. **传递性漂移**：A~桥~B 各自过阈值，A 与 B 毫不相干也进同一线索（面试并进跑步线）。增量贪心
   没有"簇内一致性"概念，一条双主题笔记就能焊死两个簇，且错误不可自愈——后续笔记只会被拉向更大的簇。
2. **拆簇不可修复**：先后形成的两条同主题线索，除非标题字符串完全相同否则永不合并；标题是 LLM
   生成的自由文本，同标题合并基本失效（两条跑步线索标题不同即是证据）。
3. **类别口径与用户直觉不符**：装修流水记成 data 后就"没有线索"，但"装修"恰是用户最想按主题回看的
   内容。THREAD_CATEGORIES 的白名单把最有叙事价值的记录排除了。

**有没有更好的方式？** 建议改法（留给修改轮，按性价比排序）：
① 重建路径改为**全量社区发现**（相似度图 + 连通分量/Leiden，簇内平均相似度约束），增量路径保持现状——
重建本来就是离线批处理，成本可控，能修掉传递性漂移和拆簇；② 线索成员变化后**重生成标题与摘要**
（摘要现在恒为空，等于线索页只有标题可看）；③ 聚类范围扩到 data（或按标签聚类作为补充维度）。
反对"如无必要勿增实体"的检验：不引入新表/新服务，只改重建算法与两个常量，符合低耦合。

## 设计深挖二：周报/月报生成——SQL 聚合口径统一后，剩下的短板在"叙事选材"

【生产实测】周报（2026-08-10~16：10 条、支出 ¥1086.60、收入 ¥8000）与月报（7 月：8 条、支出 ¥18590、
收入 ¥2200）**所有数字与本地真值一致**；敏感笔记计数入总数、正文不展示；transfer 不污染收支；
unknown_amount 单列披露。R168 把统计从 LIMIT 截断数组改为 `aggregatePeriod` SQL 聚合的决策经实测有效，
重度用户月报不会再低估——这块**当前设计是合适的**，不建议动。

**是否真的最适合？** 两个叙事层短板：

1. **栏目语义与选材不符**：周报「值得回顾的收藏」选了「试跑 10 公里成功」——这是 idea 不是 collect；
   本周语料里根本没有收藏时，LLM 硬凑栏目。建议：栏目按实际类别分布动态取舍（无 collect 则省略该栏目，
   fallbackMarkdown 已有此意识，AI 路径应对齐）。
2. **稀疏期的报告价值**：本周只有 1 条笔记时仍生成整页叙事（"你似乎花了一些时间在整理和回顾上…"），
   信息密度接近零还占推送额度。建议：笔记数低于阈值（如 3 条）时直接用简短 fallback 模板，不调 LLM。

## 设计建议

### S-1 每日回顾固定 3 席位让"悬置待办"被周年内容挤出（可靠找回：轻微）

【生产实测】语料含 2 条一年前锚点 + 1 条月度锚点 + 1 条未完成待办时，今日回顾 3 个席位全部被
year_ago/month_ago 占据，悬置待办不出现；无周年内容的安卓账号里悬置待办则正常展示。
【源码】`review.ts` 按类型优先级填满 `MAX_REVIEW_ITEMS=3`。周年纪念是"锦上添花"，悬置待办是
"别漏事"——后者更贴近可靠找回主线。建议：pending_todo 保底 1 席，或 MAX 提到 4 并类型去重。

### S-2 CSV 记账文件按行拆单（AI 整理）

即使 P1-2 修复，3 行记账 CSV 也只是一条笔记：金额字段单值，三笔支出无法入账，财务统计与
CSV 导入的账本语义不符。建议：文件提取后若识别为"日期+金额"结构的表格，提供「拆成 N 笔支出」
的确认入口（安卓分享确认页/Web 导入预览都有现成 UI 挂点）。不建议默认拆（用户可能只想存档表格）。

### S-3 分拣降级兜底的可观测性

P1-2 暴露：分拣失败在 UI 上只有「分拣中」，用户无从知道卡死还是排队；1 小时降级后也无任何标记。
建议：meta 里已有 retriage_attempts，超过 2 次即在卡片上提示「分拣遇到困难」并提供手动指定类别入口。
