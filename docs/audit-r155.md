## 2. P0-1 长搜索词导致检索 500（核心主线断裂）

**【实测】线上边界扫描**（`GET /api/notes?q=<n 个汉字>`，`[QA-R155]-a` token）：

```
q 汉字数=10 字节=30 -> 200
q 汉字数=14 字节=42 -> 200
q 汉字数=15 字节=45 -> 200
q 汉字数=16 字节=48 -> 200
q 汉字数=17 字节=51 -> 500  {"error":"internal error"}
q 汉字数=20 字节=60 -> 500
q 汉字数=30 字节=90 -> 500
```

- 同理 `?tag=` 超过约 46 字符也 500。ASCII 单词 60–80 字符同样 500。
- **【实测】UI 表现**：搜索「咖啡」正常返回；把整句「我上周在咖啡馆里想到的那个关于产品定价的点子」粘进搜索框后，时间流出现红色「internal error」横幅 + 「重试」按钮，点重试仍然 500；DevTools Network 面板可见多条 `GET /api/notes?q=…` 状态 **500**。截图：`ss_1f60e2da.png`（短词正常）、`ss_ce2389ab.png`（错误态）、`ss_12451148.png` / `ss_zoom_fbb4be3d.png`（Network 500）。
- **【实测】根因定位**：在远端 D1 直接执行超长 LIKE 模式，返回 `LIKE or GLOB pattern too complex: SQLITE_ERROR [code: 7500]`。
- **【代码】**：`backend/src/index.ts` 的 `searchTerms()` / `noteFilterConds()` 把用户输入原样拼进 5 个字段的 `LIKE ?`，没有字节裁剪；而同文件的 `/api/ask` 早就有注释明确的 `capBytes()`（"D1 rejects LIKE patterns over ~50 bytes"）。**同一约束只在一条路径上被处理**。实测印证：同一句长问题走 `/api/ask` 返回 200，走 `/api/notes` 返回 500。
- 影响面：`/api/notes` 与共用 `noteFilterConds` 的批量端点；命中「什么都能丢→AI 整理→**可靠找回**」的最后一环。用户最自然的行为（粘一句话找那条笔记）100% 失败，且错误文案是无信息量的「internal error」，未提示「关键词过长请缩短」。
- **未确认**：本轮所有注入探测（`' OR 1=1--`、`%' UNION SELECT`、`;DROP TABLE` 等）均返回 200 且无越界数据，**没有观察到任何 SQL 注入成功**。这是输入长度未收口的可靠性缺陷，不是注入漏洞。
- 修复方向（不在本轮实施）：在 `noteFilterConds` 复用 `capBytes()` 统一裁剪，或对超长词直接 400 + 明确文案；同时给 D1 错误加兜底，避免整页 500。**高内聚建议**：把「关键词 → LIKE 参数」收成一个函数，`/api/notes`、`/api/ask`、批量端点共用，杜绝同类约束再次只修一处。

## 3. R154 敏感附件信封加密全链路复核

**【代码】**信封格式：`SNE1` 魔数 + 12 字节 IV + AES-256-GCM 密文（`backend/src/crypto.ts`），`loadOriginal` 对无魔数的历史对象按明文直读（向后兼容），密钥缺失/错误时解密返回 `null`（fail-closed）。**【实测】**生产 `/health` 返回 `{"ok":true,"enc_key":true}`，密钥已配置。

**【实测】P1-2 敏感笔记去重失效**（直查远端 D1，按 `created_at + content` 分组）：

```
created_at=2026-07-11 11:33:00  n=2  is_sensitive=1  content=[加密内容]
其余 6 组                        n=1  is_sensitive=0  content=<明文>
```

【代码】根因：`import.ts` 去重用 `SELECT content, created_at FROM notes WHERE content IN (…)` 拿明文比对，而敏感笔记经敏感闸门入库后 `content` 是 `[加密内容]` 占位符，永远匹配不上 → **含密码的历史笔记每次重复导入都会多一份副本，并再写一份明文 R2 原件（叠加 P1-1）**。这恰好打在「重复导入是安全的」这一用户心智上。修复方向：去重键改为内容指纹（如 `created_at + sha256(明文)` 存一列），而不是拿可变形的 `content` 当键。

## 7. 设计质疑：2 个未审流程深挖

### 深挖 A：「重复导入」这件事真的最适合现在的实现吗？

现状：去重 = `content` 完全相等 + `created_at` 完全相等；无时间戳时退化为只比 `content`。

- 逻辑缺陷：敏感笔记的 `content` 在库里是占位符，去重必然失效（P1-2，已实测）。
- 脆弱性：只要来源导出格式微调（多一个换行、图片语法变化、标签行位置变化），`content` 就变，历史笔记会整批重复入库；用户对「我是不是导过了」本来就没有记忆，产品又鼓励「一键导入」。
- 更好的方式（建议，不在本轮实施）：① 去重键用**规范化正文的指纹列**（`import_fingerprint`，敏感笔记在加密前算），配唯一索引，让数据库而不是应用层保证幂等；② 导入前给「预检结果」——本次 8 条中 7 条已存在、1 条新增，让用户确认后再写；③ 把 `import_source + 原始 ID`（flomo/Cubox 导出里通常有）作为首选幂等键，内容指纹只做兜底。这同时消掉 P1-2 与「重复导入放大明文附件」的复合风险。

### 深挖 B：账号恢复（恢复码 → 密码/token/恢复码三轮换）之后，用户的多端怎么办？

**【实测】**`POST /api/auth/recover` 成功后：新密码可用、返回新 token 与新恢复码、旧 token 立刻 401。安全语义正确。但产品语义不完整：

- 用户此刻在 Android、剪藏扩展、MCP 客户端上的凭据**全部静默失效**，恢复流程的返回页没有任何「你还需要在 X/Y/Z 重新登录」的引导，也没有「已在其他设备退出登录」的说明。用户的体感是「我恢复了账号，结果手机和插件都坏了」。
- 恢复码是一次性的：轮换后旧码立即作废，若用户没保存新码，下一次就没有恢复手段；当前流程只把新码放在响应里（**【未验证】**Web 恢复页对新恢复码的展示/下载/二次确认交互本轮未走查）。
- **D-3**（【实测】+【代码】）：登录限流维度含 `acct:<用户名>`，任何人对已知用户名连打 5 次错误密码，就能让真实用户 1 分钟内登录 429。持续打即持续锁定。这是「防暴力」与「可用性」的经典取舍，当前实现偏向前者且没有区分「同一 IP 的连续失败」和「分布式打同一账号」。建议：账号维度改为渐进延迟 / 需要人机验证，而不是硬 429；或账号维度只在多 IP 失败聚集时才升级。
- 更好的方式（建议）：恢复成功后给一屏「安全摘要」：新恢复码（要求勾选"我已保存"）+ 已失效端列表 + 一键跳到各端重新配置的指引；`/api/auth/me` 增加「上次凭据轮换时间」，让各端能提示用户而不是直接 401 白屏。

### 附带设计建议

- **D-1**：【代码】Android `pollTriage()` 每 2s 拉一次**当前筛选下的整页列表**、最多 15 次（30s）；Web 只轮询单条笔记。同一需求两套实现、移动端还更费流量；30s 后放弃且不提示，慢分拣仍会留下滞留的「分拣中」。建议统一为一个轻量批量状态端点（传 id 列表返回 category/title），Web 与 Android 共用。
- **D-2**：【代码】`retriageUnsorted` 是**全局**队列：`ORDER BY (category IS NULL) DESC, created_at ASC`、`LIMIT 25`、并发 5、时间预算 8 分钟，没有按用户的公平性；导入的旧时间戳笔记天然排在新捕获笔记之前。一个用户导入几千条历史，就能把其他用户「刚记的那条」的分拣推到后面几轮。**【实测】**本轮 34 条（两账号）在约 25 分钟内全部落定分类，未复现饿死，故仅作设计风险记录。建议加按用户轮转（每轮每用户取 N 条）。
