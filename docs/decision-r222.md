# R222 修改轮决策记录（落实 audit-r221）

对应审查报告：`docs/audit-r221.md`（R221 终定 GO：2 个 P1 + P2×4 + P3×5）。统一管道原则：全部收口在既有管道内，不新增平行逻辑。

## 1. P1-1 生产 API 间歇 ~60s 请求挂起 → 归因：客户端连接级悬挂；收口在 Web 请求层

先归因后动手（一手证据）：

- **源码检查**：AI 上游并非无保护——Workers AI 走 `withTimeout`（默认 20s），OpenAI 兼容通道走 `AbortSignal.timeout`，嵌入 8s/30s 双档；排除「AI 上游无超时」假设。
- **Worker 侧指标**（Cloudflare GraphQL workersInvocationsAdaptive）：请求 duration 分位数普遍很低，无 60s 级 CPU/duration 尾部；个别小时 wallTime P99 偏高但与审查复现时段不对应。
- **直连压测**（本机 curl，/api/health 与 / 各 100 发）：P50≈66ms、P95≈79ms、P99≈84ms、max≈122ms，零超时零 60s 尾部。
- **浏览器实测**（Chrome fetch×40）：12–40ms 全部 200。
- **测试环境自述**：`.agents/skills/testing-prod-ui/SKILL.md` 明确记载本测试机浏览器会偶发 ~60s 假挂起而同机 curl 正常——与 audit-r221 复现形态（重试即恢复、直连 API 复测 ~790ms）完全一致。

结论：现有证据一致指向**浏览器/网络连接级偶发悬挂**（单条连接卡死，换连接立刻恢复），而非 Worker CPU、D1 慢查询、AI 上游或 cron 争用。服务端不加任何「掩盖性重试」；在真正责任边界（Web 请求层）做超时隔离：

- `web/src/lib/api.ts`：交互 GET 兜底超时 60s → **20s**（服务端读路径 P99 远低于 1s，挂满 20s 只可能是连接级悬挂，早断早重试优于白等）；**幂等 GET 超时自动重试一次**（换连接即恢复）；写请求保持 60s 且**不自动重试**（避免重复写，离线兜底走既有 outbox）。
- 修后压测（部署后复测）：P95/P99 无 60s 尾部，证据见 PR。

## 2. P1-2 周报/月报分类计数 LLM 转写偏差 → 修复（数字全部模板注入，LLM 只写叙述）

根因：`reports.ts` 生成报告时 `if (text) md = text` 用 LLM 原文**整体替换**确定性 markdown，SQL 数字只作为提示词参考，模型抄错即出错（audit-r221：月报 58/59、想法 13/14；周报资料 5/6、资金往来 2/1）。

修复（`backend/src/reports.ts`）：

- 标题、`## 概览` 统计行（`overviewStatLine`，总数/分类计数/敏感数）、`## 待办盘点`（`todoSection`，支持本周/本月单位）、`## 收支合计` 全部**程序拼接**，数字直接来自既有 `aggregatePeriod` SQL 聚合与 todo/finance 统计，不经 LLM。
- LLM 提示词改为只写叙述（主线故事/主要在想什么/悬而未决/值得回顾的收藏），明确禁止输出总数、分类计数、待办计数、收支合计。
- 输出后校验兜底（`sanitizeNarrative`）：即使模型仍在叙述里写了「共记录 N 条」「X 分类 N 条」「新增待办 N 条」等，一律**回写为 SQL 源值**；剥重复 H1/概览标题；丢弃模型擅自输出的待办盘点/收支合计小节。
- 锁定：`test/r222-fixes.test.ts` 以 audit-r221 实测错抄样本为用例，锁住周报/月报全部数字项与 SQL 口径一致。

## 3. P2×4 逐条

- **P2-1 链接抓取失败提示 → 修复**：`fetchArticleDetailed` 记录失败归因（404/403/HTTP 错误/超时/非 HTML/网络），存 `meta.link_fail_reason`（成功时 json_patch null 清除）；Web 卡片文案按归因区分「页面不存在（404）/网站拒绝抓取（403）/抓取超时可重试/链接不是网页」等，不再统一含糊说「未能抓取正文」。真实站点抓取成功率验证并入本轮 QA。
- **P2-2 周报内 URL 渲染畸形 → 修复**：报告叙述经 `sanitizeBareUrls` 把裸 URL 用尖括号收口并剥落尾部标点，中文标点/后续文字不再被 marked 吸进链接锚文本；单测锁定。
- **P2-3 「充话费 100」判 todo 丢金额、「给我爸买按摩仪 599」判 income → 修复**：`triage.ts` 提示词补两条生产原文判例（动宾+金额省略句默认已发生记账；「给某人买/送」是与格短语不是收款，只有「给我转/发/报销」才是 income）；`scripts/triage-eval.ts` 补同名 eval 用例锁住。
- **P2-4 重度突发分拣收敛偏慢（150 条 ~29 分钟）→ 修复（最小改动）**：分拣扫描并发 `RETRIAGE_CONCURRENCY` 5→10（IO-bound，远低于提供方限额），单个 10 分钟 cron 周期内即可清完一次重度突发导入；不改调度结构、不加新实体。

## 4. P3×5 逐条

- **P3-1 弱网首屏 ~2s 纯白 → 修复**：`web/index.html` 内联 `#root:empty` 骨架样式（纯 CSS，明暗双色跟随系统），JS 包下载/解析期间显示占位骨架，React 挂载即被替换；不增加任何运行时开销。
- **P3-2 请求超时提示文案 → 修复（与 P1-1 同一收口）**：GET 20s 超时 + 自动重试一次；仍失败时既有 `NetworkError("请求超时，请重试")` 文案链路展示，注册路径保留幂等重试专用文案。
- **P3-3 离线排队笔记无时间流占位卡片 → 不改（论证）**：decision-r206 §6 已系统评估过——时间流伪造 pending 卡片需伪造 Note 实体、与真实笔记生命周期冲突（违反「如无必要勿增实体」），已用 outbox 预览横幅（可展开查看排队内容+立即重试）做最小闭环。本轮维持该口径。
- **P3-4 问答聚合口径两处缺口 → Q24 修复，Q21 待生产复核**：
  - Q24「最近一个月最关注的三个主题」：新增主题归纳确定性路由（`topicSummaryIntent`/`buildTopicSummaryAnswer`）——按标签频次 SQL 全集统计 top-N（敏感笔记标签不展示），并提示叙述性回顾在周报/月报；不再径直「没找到」。
  - Q21「这个月记了几笔支出」：本地对 main 代码逐路由复核，该问法及常见变体**均已命中财务精确聚合（exact）路由**，应输出确定性笔数；审查观察到的退化无法离线复现（疑与多轮改写上下文有关）。本轮生产 QA 原句复测：命中确定性数字则记闭环，仍退化则带证据进 R223。
- **P3-5 注入文本回显 → 不改（论证）**：审查已证实 5 种注入语料均被当普通笔记，未执行任何指令、未跨租户泄露；「注入原文出现在检索/问答引用中」是忠实呈现用户自己的笔记内容，属预期行为而非漏洞——对用户自有内容做改写/遮蔽反而破坏数据忠实性（用户看到的引用应与其所记一致）。执行面已有系统提示词隔离与确定性路由护栏，维持现状。
