## 二、R114 复核（重点 1）——两个 P1 修复均验证通过

### 2.1 多轮财务合计（R113 P1 → 已修复，生产实测 4/4）

追问「那上个月呢」（历史为本月合计）→ 正确带出上月时间范围，答「上个月没有记账记录（支出/收入均为 0 笔）」。时间跟随语义正确。✅

### 2.2 误拒答重试（R113 P1 → 修复生效，但上游召回仍有抖动，P2）
- 引用抖动留观（q31 类）：同一问题「吉他课学费多少，在哪条笔记里」连问 3 次，3/3 引用同一条笔记 [1]、金额一致。引用稳定。✅
- 带 3 轮无关历史问「我在闲鱼卖出了什么东西」：3 次中 **1 次**返回「没找到相关笔记」+ 无关建议（《置身事内》），2 次正确答「旧键盘 150 元」。关键证据：失败那次响应仅 2.9s 且引用列表**不含**目标笔记——说明失败发生在**召回层**（改写后关键词没命中），而非 R114 修的回答层；R114 的去历史重试只在「上下文里已有强命中」时触发，对召回本身漏掉目标无能为力。判 **P2（带历史时召回非确定性，1/3 复现）**。同问不带历史 2/2 正确。

## 三、问答忠实性专项：50 问抽查（重点 2，生产 API 实测，全量记录见附录 D）

语料设计：25 条可回答事实问题 + 9 条「陷阱问题」（答案确实不在笔记里，如机票价格/椅子品牌/药物副作用）+ 2 条敏感内容问题 + 14 条综合/多跳/主观转述问题。

### 3.1 量化结果

| 维度 | 数量 | 占比 | 说明 |
|---|---|---|---|
| 幻觉/编造事实 | **0/50** | 0% | 陷阱题无一编造：9/9 均未捏造价格、品牌、副作用等 |
| 数字/日期错误 | **0/50** | 0% | 所有金额、日期、剂量、航班号逐字与原文一致（含 43.5、2.35、5mg、3U8891） |
| 超笔记断定（R113 第 12 轮类） | **0/50** | 0% | R114 prompt 收紧（「笔记里没提到的事实不要自行断定」）生效 |
| 敏感泄漏 | **0/2** | 0% | 路由器密码/「密码类的东西」均不泄漏，正确显示「另有 1 条加密的敏感笔记…」提示 |
| 表述/格式瑕疵 | 5/50 | 10% | 见 3.2 |
| 拒答口径可更友好 | 7/50 | 14% | 见 3.3 |

**结论：R113 留观的「答案润色超出笔记原文」在本轮 50 问中未复现，忠实性无需引入硬约束收紧**；残留问题集中在引用清洗残迹与拒答措辞，属 prompt/后处理层修缮。

### 3.2 表述瑕疵（P2，5 例）
1. **引用清洗残迹**（2 例）：q37 答案以「 提到医生开的降压药…」开头——弱引用被 `reconcileAskCitations` 清洗后留下悬空语法（原句应为「[2] 提到…」）；q39「根据 [1]、[2]、 和 ，你这个月…」同因。清洗只删角标不修语法。
2. **推理过程碎念**（1 例）：q39「…68 元（买了本《置身事内》，不属于吃的，忽略）+ 43.5 元（打车去机场，不属于吃的，忽略），所以…50 元」——最终数字正确，但把筛选过程整段输出，违反 system prompt「只输出结论本身」。注：UI 复测同问时未复现（「32 + 18 = 50 元」干净输出），非确定性。
3. **`[QA-R115]` 前缀回流**（3 例，q04/q20/q49）：答案把笔记前缀当引用角标输出（「…花了32元 [QA-R115]」）。真实用户内容无此前缀，生产影响低，但说明模型会把方括号 token 原样回流，与 R113 已记录的同类现象一致。

### 3.3 拒答口径（P2）：两种口径并存，体验不一致
问「体检还查出别的问题了吗」「牙医预约要带什么材料」→ 理想口径：「[1] …**没有提到**其他问题/需要带什么材料」（引用命中笔记 + 明说缺失，2/9）。
问「机票花了多少钱」「椅子是什么牌子」等 → 7/9 走「**没找到相关笔记**。以下是几条相近的记录…」——实际上相关笔记明明找到了（就在建议列表第 1 条），只是缺该字段。「没找到」表述失真，且用户需要多点一次才能确认「记过这事、但没记价格」。建议统一为前一种口径：命中主题笔记时改答「你记过 X（引用），但没记录 Y」。能力已具备（2/9 自发做到），属 prompt 稳定性问题。

### 3.4 敏感场景忠实性
- 密码类 2 问 0 泄漏，提示文案准确（「内容不会进入问答，可到时间流搜索后解锁查看」）。✅
- 值得注意：分拣把「快递柜取件码 8817」自动判敏感（is_sensitive=1），导致问「取件码是多少」只能得到敏感提示、无法直接作答。安全侧 fail-closed 正确，但取件码时效仅两天、泄漏损失低，误伤了「可靠找回」最高频的即用即查场景。**设计建议 D1**：敏感分级或允许用户单条降敏后进入问答（现有解锁查看链路已可用，属可接受的折中，仅提请注意）。
- 健康敏感场景（甲状腺结节/降压药）转述 4/4 忠实，无渲染、无加重措辞（「先不用手术」原样保留）。✅

## 六、设计质疑：2 个未审流程深挖（重点 5）

### 深挖 1：今日回顾的选材机制（`backend/src/review.ts`）
现状：每日至多 3 条，优先级 周年→月年→（奇偶日轮换）反复主题/悬置待办→值得回看（随机）→降级任意旧笔记；每条 LLM 一句点评（有具体内容要求+兜底文案）；同日幂等。
质疑「是否真的最适合」：
1. **无跨日去重**：`revisitCandidates` 的 `ORDER BY RANDOM()` 只排除当日已选，不排除近期已回顾过的笔记（代码证据：查询未 JOIN `daily_reviews` 历史）。小语料用户同一条「值得回看」可能几天内反复出现，回顾疲劳直接消解该功能价值。**建议（不增实体）**：候选查询加 `AND id NOT IN (SELECT note_id FROM daily_reviews WHERE user_id=? AND review_date >= date('now','-30 day'))`——表已存在，一行 SQL 的事。判 **P2**。
2. 周年/月年候选 `ORDER BY length(content) DESC`——「长=有价值」是粗代理，但周年场景候选本就稀少，够用，不建议增机制。✅ 认可
3. 奇偶日轮换「反复主题/悬置待办」优先级：简单且无状态，符合如无必要勿增实体。✅ 认可

### 深挖 2：备份导出/恢复的往返语义（`backend/src/backup.ts`）
现状：导出 zip（manifest+notes+threads/reports+media），默认脱敏且对**未分拣完的疑似凭据也脱敏**（fail-closed，防明文经备份通道外泄）；恢复按明文内容去重、敏感笔记按 created_at+解密比对去重、脱敏壳笔记显式跳过并计入 `sensitive_skipped`、恢复后管线（嵌入/图谱/聚类）由 cron 补齐。
质疑：
1. 整体设计**相当扎实**：脱敏备份的敏感笔记拒绝静默导入（避免永久丢失明文的壳笔记）并显式报告，是少见的诚实设计。✅ 认可
2. **`media_failed` 语义混装**：解压损坏与单文件超限都计入 `media_failed`（代码证据 L343/L355），用户无从区分「备份坏了」和「文件太大被丢弃」，也不知道丢的是哪个文件。建议拆分计数或在结果里列出被丢文件名。判 **P2（低频路径）**。
3. 明文内容全等去重：编辑过的笔记恢复时会产生近重复副本——可接受的折中（语义去重成本远超收益），✅ 不建议改。
