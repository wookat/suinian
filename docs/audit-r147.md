## 5. 设计质疑（2 个未审流程深挖）

### 5.1 恢复码找回流程（`POST /api/auth/recover`）【源码走读】
- 现设计：用户名 + 一次性恢复码 → 重置密码 + 旋转 API token + 换发新恢复码；统一 401 防账号探测；IP+账号双维度限流；PBKDF2 哈希存储。
- 质疑"是否最适合"：**基本是**。在无邮箱/手机架构下，一次性消费 + token 旋转 + 换发新码的闭环把"码泄露"的窗口压到单次；统一 401 与限流挡住枚举。剩余风险：恢复码是单因子，泄露即完全接管（改密+旋 token 把原主挤下线）且原主无任何感知通道。建议（不定级）：恢复成功后在旧会话/下次登录处给出显式提醒，或恢复后 24h 内保留旧 token 只读观察期——按"如无必要勿增实体"权衡，提醒比观察期更轻。

### 5.2 完整备份/恢复流程（backup.ts）【源码走读 + 生产 UI 核对】
- 现设计：流式 zip（内存有界）；脱敏备份的敏感闭包覆盖派生明文（meta 转写/URL 摘要）与附件原件；恢复不信任 zip 内 `is_sensitive` 定论、统一走持久层敏感管道防篡改绕过；占位壳笔记显式跳过并计数。整体是全仓库设计密度最高的模块之一，**闭环合理**。
- **P2-3：恢复路径绕过 R146 mime 兜底**：`storeMedia` 直接 `MEDIA.put(..., contentType: att.mime ?? "application/octet-stream")` 并按原 mime 写 attachments 行，未复用 `resolveAttachmentMime`。恢复 R146 之前导出的旧备份（内含 octet-stream 音频）会把 R146 刚清零的存量问题重新引入。顺带的结构问题：恢复媒体没有复用 `storeOriginal`，形成第二条媒体入库路径（违反"如无必要勿增实体"）——建议实现方收口到 `storeOriginal`，mime 兜底自然生效。
