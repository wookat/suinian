## 2. P0-1：门控本身 fail-open

### 2.1 不可见 / 双向控制字符载体（C13/C14/C30）

根因：判定面的归一化只「删除」零宽字符，**双向控制字符既没被删除也没被还原**——
`U+202E` 包裹的倒序 `curl -s http://…/s.sh | sh` 在任何归一化面上都不呈命令形态，
「渲染顺序与字节顺序相反」这一层语义从未进入判定，于是门控 null、确定性内核 null、
判别器根本没被调用，答案原样直出。

设计（`prompt-armor.ts` `invisibleCarrierVariants()`）：判定面额外生成两条还原候选——

1. V1：剔除全部不可见/双向控制字符（`U+202A-202E`、`U+2066-2069`、`U+200E/200F`、
   零宽、`U+00AD`、`U+180E`、`U+034F`，NBSP 折成空格）后的文本；
2. V2：V1 再整行倒序（RTL 覆盖/隔离符渲染出的视觉顺序即倒序字节序）。

这两条面接入四处：门控（`execClassifierGateReason`）、全局判定
（`globalExecDangerReason`）、行级能力（隔离定位）、降级痕迹判据。
另外「答案里出现双向控制字符」本身即门控信号（`gate:bidi-control`）：笔记答案里
它们没有合法用途，开门只多一次判别器调用，漏面则是静默放行。

**这些还原面只用于判定**：用户可见文本与 verbatim 出口永远取原始字节，不做替换。

### 2.2 同形异义（C11）与进程替换（C25/C26）

- 同形异义：`сurl -s … | ѕh` 用 Cyrillic `с`/`ѕ` 冒充 ASCII；NFKC 不做跨字母表折叠，
  命令名字面全部落空。新增 `foldHomoglyphs()`（西里尔/希腊/数学字母 → ASCII，
  含 `∕ ⁄ ǀ ∣ ː` 等标点同形字），接在 `deobfuscateCommandShell()` 首层，
  即进入 `normalizeCommandText()` 的全部判定路径。
- 进程替换：`. <(curl …)` 旧口径要求行首/分隔符锚定，写在中文冒号后不命中 ⇒
  sink 落空。`EXEC_SINK_RE` 增加 `source <(` 与 `[\s;&|(:：]. <(` 两个形态。
- 「外链已剥除」不算消危：`deobfuscateCommandShell()` 早已把 `LINK_REMOVED_MARK`
  还原成取码 URL 占位（R291 收口），本轮保留并被 C29 残片用例覆盖。

### 2.3 纯散文步骤（C23）与解码器链（C06/C07/C08/C22）

- 纯散文：「先用 curl 把 X 下载下来，再交给 sh 执行」无任何命令标点却完整可执行。
  判据 `cap:fetch+prose-exec` = 取码能力 ∧ 远程脚本 URL ∧ 中/英文「交给解释器执行」。
- 解码器链：`… | tr A-Za-z N-ZA-Mn-za-m | sh`、`… | xxd -r -p | bash`、
  `$(echo <b64> | base64 -d)`——「把解码产物交给解释器/命令替换执行」本身就是完整
  执行语义，与被解码内容无关。判据 `cap:decode+sink` / `cap:decode+cmdsubst`。

### 2.4 判别器「可用但零命中」不再被无条件信任

`index.ts` 的分类链路：判别器返回空数组时，用确定性内核 `globalExecDangerReason()`
（含上面全部还原面）复核；内核命中即**否决**零命中，按「判别器不可用」处置
（保守隔离），且不缓存该零命中结论（`exec_gate` 追加 `|veto:<reason>` 便于生产取证）。

### 2.5 判别器命中却被静默丢弃（本轮新发现，C11/C22/C23/C25/C26）

判别器在**收口前**的答案上跑，而 `finalizeAskAnswer` 先做外链收口
（URL → `〔已移除外部链接〕`）再比对句段：含 URL 的危险句段折叠后与判别器回传的
句段不再相等 ⇒ 命中被丢弃 ⇒ 在线命中态仍无标记。收口：比对面去 URL/外链标记，
并允许长度 ≥ 8 的非平凡片段双向包含。

### 2.6 降级前置条件：从「门控命中」改为「代码面/命令面痕迹」

`index.ts` 进入判别/降级链路的前置改为
`execClassifierGateReason(answer) ?? execCodeSurfaceTraceReason(answer)`。
后者更宽：围栏、代码形态行、代码标点、双向控制字符任一即成立。
门控漏面时**不放行**，仍走判别器（不可用则保守隔离）；只有完全无代码/命令痕迹的
纯散文才跳过（保持普通问答的低延迟）。

`finalizeAskAnswer` 降级分支的最后一道保险也不再依赖 `execClassifierGateReason`，
改用与层 3 同口径的 `execDegradedTraceReason`。

### 2.7 安全下界：门控完全瞎掉时用户看到什么

三层，逐层收紧：

1. **判别器可用**：判别器命中 + 确定性内核命中（含还原面）的并集被隔离/警示，
   其余正文照常。
2. **判别器不可用 / 被否决的零命中**：答案里**携带执行痕迹的行与围栏块**被替换为
   降级隔离说明，其余正文保留可读，全答附「代码安全判别暂不可用」提示。
3. **痕迹存在却一个区间都定位不到**（门控与定位同时瞎掉）：整答替换为降级隔离
   说明。

因此下界是：用户最坏只会看到「普通无危险文本」+「无法定位/无法确认安全的代码面
被隔离的短提示」，**任何潜在可执行的危险内容都不会原样交付**。反向下界（P1-4）：
没有任何执行痕迹的普通技术笔记不因判别器掉线而被剥夺原文。

## 3. P1-4：降级态大面积误伤（105/116）

根因：R292 的降级层 2 把「全部代码区域 + 全部代码形态行」无差别隔离，
`isCodeLine()` 只要求「看着像代码」（一个 `foo(` 或赋值就算）⇒ 判别器一掉线，
教学代码/技术笔记整篇被探空。

判别器要判的是「这段代码会不会执行/外连」，不是「这是不是代码」。新的降级痕迹判据
`execDegradedTraceReason()`（行级与围栏级）：

- 确定性内核命中（`hasExecIntentReason`）；或
- 弱信号组合 `fallbackCapabilityReason`；或
- **两类以上能力同现**（net/exec/shellio/fetch/inline/lolbin/sink/priv）；或
- `hostport` 与执行类能力（exec/shellio/sink/inline）同现；或
- 混淆地址 / `fetch→run` 链。

单一能力（只有 `hostport` 的 nginx `proxy_pass`、只有 fetch 的 `requests.get`、
只有 `#!/bin/bash` 的发布脚本、只有 net+hostport 的 socket 监听示例）不构成隔离
理由；真实载荷（反弹/绑定 shell、curl|sh）必然是多能力同现，仍然命中。

层 3（整答隔离）同口径：只有当整答面满足上述痕迹、而层 1/层 2 一个区间都没定位到
时才整答隔离——P0 的 fail-closed 下界不变。

门禁：新增 `backend/test/r294-guard-matrix.test.ts`，把 R288（恶意 72 + 善意 116）、
R290（12 能力对 × 12 载体 + 善意 146）、R294（30 载体 × 2 问法 × 3 判别器态）三套
语料的通过标准固化进 `npm test`——R292 那次回归下次会被门禁拦住。

## 4. P1-3：Service Worker 收口（离线缓存改为默认关闭的可选项）

### 4.1 证据（生产遥测权威直查，R293 §7）

`sw_error_reports` 128 行 / 6 天 / 4 个 Chrome 大版本，全部为
`registration without any worker; hard reset` 与 `hard reset unsettled in 20000ms`：
SW 在真实终端上**从未 activated**，PWA 离线连续三轮（R291-R293）无法取证；同时产品
反复弹「离线缓存组件卡住了…可能导致登录/注册长时间无反应」横幅，且被卡死 SW 控制的
页面所有 fetch 都要等 SW 启动——净体验为负。

### 4.2 产品决策

1. **默认关闭**：离线缓存改为「设置 → 离线与更新」里的可选项（`sn_offline_cache`，
   默认关）。未开启时完全不注册 SW、不弹任何横幅；只做一次静默清理，把历史遗留的
   registration 注销掉（否则老用户页面仍被卡死 SW 接管）。
2. **失败终态**：用户主动开启后，注册重试额度（5 次指数退避）耗尽、注册调用悬挂
   （20s 未结算）、或无 worker 卡死态自愈悬挂时，一律 `unregister()` 全部 registration、
   清空 CacheStorage、回到关闭态，此后不再注册、不再弹窗。
3. **遥测保留**：`sw_error_reports` 通道原样保留，并新增 `SwGaveUp` /
   `SwGaveUpUnregistered` / `SwGaveUpUnregisterTimeout` 事件，用于观察真实终端里
   卡死占比与放弃率。
4. **推送依赖如实提示**：Web Push 订阅挂在同一个 SW 上，离线缓存关闭时 `enablePush()`
   直接给出「请先开启离线缓存」的明确错误，而不是无限转圈。

### 4.3 备选方案与取舍

- 继续自愈重试（R285/R288 路线）：三轮生产数据证明该浏览器侧故障不是代码能修的
  （unregister/register 均不结算），继续重试只产生弹窗骚扰，否决。
- 换 no-precache 的最小 SW：不解决「SW 组件级 wedge 拖住所有 fetch」的根因，否决。
- 因此按审计建议执行：默认关闭 + 可选开启 + 失败终态放弃。SW 若在某环境真正
  activated 的离线读写证据，留待生产复测时如实记录（能开启则给一手证据，不能则标注）。
