## 6. 设计质疑：两个未审过流程深挖

### 6.1 敏感内容全旁路审计（线索/周报/MCP）✅ 设计自洽

质疑：敏感笔记明文是否可能从问答以外的旁路（线索摘要、周报、MCP）泄露？逐路核验：

- 线索：`threads.ts` 全部候选 SQL 带 `is_sensitive = 0`，敏感笔记不参与聚类/摘要/代表向量；生产验证两条敏感笔记 `thread_id` 均为 null。【源码审阅 + 生产实测】
- 周报：`reports.ts` 敏感笔记只进计数（总数口径对齐），标题/内容一律排除（`filter(!is_sensitive)`）。【源码审阅】
- MCP：见 5.2，list/search/get 三路均脱敏。【生产实测】

结论：旁路无泄露，"计数包含、内容排除"的口径统一且合理。无发现。

### 6.2 MCP 破坏性操作语义（delete_note/restore_notes）✅ 设计合理，1 条设计建议

质疑：把删除能力暴露给第三方 AI 客户端是否安全、是否最适合？

- `delete_note` 为软删除且返回提示"30 天内可用 restore_notes 恢复"，工具描述引导先 search 后删——不可逆风险已被软删+提示兜住。【生产实测 + 源码审阅】
- 跨用户隔离：用 A 账号 token 删 B 账号笔记 → 404，B 笔记未受影响（MCP 工具复用 REST 鉴权，隔离继承自 API）。【生产实测】
- `restore_notes` 批量恢复正常（restored:1）。【生产实测】
- **设计建议 D-1**：`delete_note` 无二次确认参数（如 `confirm: true`），完全依赖上游 AI 客户端的确认习惯；若客户端提示词不严谨，用户一句含糊的"清理一下"可能触发误删。虽有 30 天软删兜底，建议在工具入参或描述中加一层显式确认约定。不影响核心主线。
