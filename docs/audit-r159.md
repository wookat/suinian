## 6. 设计深挖（2 个未审流程）

### 6.1 账号找回/恢复码流程（`/api/auth/recover`）

优点【代码】：一次性恢复码 hash 存储、用后即换新码、成功后全量 token 轮换（泄露 token 随旧密码作废）、未知用户/错码统一 401 防探测、IP+账号双限频。设置页有「重新生成恢复码」入口。

质疑：
1. 注册时恢复码生成失败静默吞掉（`catch → recoveryCode = null`），前端拿到 null 后用户既不知道、也没有恢复途径，直到主动去设置页 → **D-1**。
2. 每次 recover 成功都返回**新**恢复码，用户在慌乱找回场景下极易不记录新码——下次忘密码即永久锁死（无邮箱/手机绑定是产品选择，但「码用一次就换」将单点失败概率翻倍）。建议 recover 响应页对新码做强制确认式展示。

### 6.2 批量操作「选中全部匹配」（`POST /api/notes/batch`）

优点【代码】：服务端按当前过滤条件解析目标、单批 1000 上限 + `remaining` 回报、NDJSON 流式进度、echo ids 支持一键撤销、批量写限频（R123 修复保持）。

质疑：
1. 客户端「自动续删到清空」的循环没有时间快照：循环期间微信/API 异步新写入且命中过滤条件的笔记会被顺手删除，用户从未见过它们 → **D-2**（低概率但违反最小惊讶）。
2. `stream=1` 路径用 `waitUntil` 继续执行——客户端断开后删除仍在进行，符合预期但 UI 无从得知最终结果；撤销 ids 若未收到最后一行 NDJSON 即丢失撤销能力（可接受的权衡，记录在案）。
