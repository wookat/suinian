## 2. 专项：财务方向兜底架构健康度

### 2.1 语料量化【生产实测】
64 条方向语料（购物/收入/退款/垫付/未还欠款/转账/内转/代付/礼金红包/AA 平摊/还债/未来转账待办 全场景）经 `POST /api/notes` 入库并等 AI 分拣：

- **分类正确 62/64 = 96.9%**；语料中标注了期望金额的条目金额全部正确（100%）
- 误判 2 条：
  1. 「房客交了下季度房租 9000」→ expense（应 income）：`EXPENSE_DIRECTION_RE` 的「交了」不辨主语，他人交钱给我被判为我方支出
  2. 「垫付快递费 23，同事微信还我了」→ transfer（应 income/expense）：`fixTransferMisfile` 先翻成 transfer，而 `fixAaReimburse` 的 `AA_REIMBURSE_RE` 要求「垫付…还我」间距 ≤10 字符，本句恰好超窗，第二段翻转未触发

### 2.2 源码级诊断【源码检查】
`backend/src/triage.ts`：13 个 fix* 兜底函数、40+ 条正则、历史 43 次提交（R118→R210→R216→R218→R220→R222 多轮补丁）。管线顺序：
stripMarkerNoise → fixFinanceDirection → fixTransferMisfile → demoteEventLog → fixLedgerCategory/Amount/ReceiptDoubleCount/LedgerNetDirection → fixProseTotalDirection → fixAaReimburse → fixSplitBillAmount → fixAdvanceRepayAmount → fixWeekdayDue。

碎片化征兆（客观存在，但尚未失控）：
- **三套独立的"提醒词表"**（`REPAY_PENDING_RE`、`SELF_ACTION_RE`、`TRANSFER_INTENT_RE`）语义相近、成员不同，改一处易漏两处
- **两段翻转链**：垫付回款类依赖 fixTransferMisfile(→transfer) + fixAaReimburse(→income) 接力，第二段受正则字符窗口（≤10 字）限制，误判 #2 即此类边界
- **主语盲区**：方向正则纯词面匹配，无法区分「我交了钱」vs「别人交了钱给我」，误判 #1 即此类，正则不可根治

### 2.3 架构评估与建议（只诊断不改）
**不需要整体重构**：96.9% 的实测正确率、金额 100%、报告数字确定化后，规则族仍在有效工作且相互冲突尚未成灾。现有架构已经是「LLM 主判 + 规则兜底」形态，符合公司"规则只做 fail-closed 兜底"的方针。建议方向（供 R224+ 决策）：
1. **停止给方向类正则打新补丁**：主语类误判（他人「交了/付了」给我）属语义问题，应回流到 LLM 提示词 few-shot（decision-r222 已建立此通道），正则续补只会加深碎片化
2. 合并三套提醒词表为单一常量，消除同义不同表
3. 给「垫付…还/转」类去掉 10 字符窗口或放宽到整句，消除接力翻转对窗口的敏感
4. 为 fix* 规则族补一份 conflict 矩阵测试（同一句被多条规则先后改写的组合用例），锁住管线顺序语义
