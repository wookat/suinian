### 2.3 【P1-2】非财务聚合/枚举类问题会自信错答【生产实测 + 代码证据】

- 生产实测：`[QA-R123]-main` 库内确有 210 条（D1 实查 `COUNT(*)=210`），`/api/ask` 回答"你一共记了 16 条笔记"——16 恰是本次召回条数。同一账号 `GET /api/stats` 返回的 `total_notes` 是正确的 210，即**正确答案就在同一进程一次 SQL 之内，却没被使用**。
- 代码根因【代码证据】：`backend/src/ask.ts` 的 fail-closed 只针对财务口径——`financeAggIntent()` 要求 `FINANCE_WORD_RE`（花/支出/收入/结余…）先命中，才会进 `exact`（走 `financeStats` 精确 SQL）或 `fail_closed`（拒绝心算）。"多少条笔记""这周记了什么"不含财务词，直接落到普通 LLM 召回路径，而召回是 `LIMIT` 截断的 top-k，于是 LLM 对片段数量心算。
- 对比证据：问题 25「今年在吉他上一共花了多少钱」被正确 fail-closed（"暂不支持按限定条件精确合计…我不做心算合计"），问题 26 却给出确定数字。**同一产品里，含"花钱"二字的问题受保护，不含的不受保护**——这是 R107 引入财务 fail-closed 时留下的同型缺口，不是新逻辑错误。
- 影响核心主线：**是（可靠找回）**。用户对"一共/多少条/都记了什么"这类问题没有校验手段，一次自信错答会直接摧毁"可靠"这一承诺。

### 2.4 时间窗与多候选：两个不算 bug 但影响体感的点

- 问题 23「这周我都记了些什么」：本周实际有 6 条，答案只覆盖 3 条。时间窗类提问走的仍是语义 top-k，而不是"按 `created_at` 窗口全量枚举再摘要"——`stats.daily` 已有精确的按日计数，同样是"数据在手却没接进 ask"。
- 问题 1「上个月存的那个什么管理的文章」：库里同期有"知识管理""注意力管理""需求管理""技术债"多条，系统只取了一条最相似的直接作答。**模糊提问天然多候选，正确设计应是"我找到 3 条'…管理'的文章，你说的是哪条"式的枚举 + 追问**，而不是替用户选一条。这条按判定口径记未命中，但答案本身并非错误。

### 【P2-2】押金往返不对账

押金**退回**判 transfer，押金**交付**判 expense：一次完整的租房押金往返在账本上留下 −3000 的支出和一笔不计入收支的 transfer，净额永远差 3000。`backend/src/triage.ts` 里 `DEPOSIT_REFUND_RE` 只匹配"退/返/还回"方向，交付方向没有对应规则【代码证据】。按 R122 自己的定义（"押金是拿回自己的钱/可收回的资金平移"），交付方向理应同为 transfer——**同一语义的两个方向用了两套口径**，与 D3 是同一类问题。影响核心主线：是（AI 整理的可对账性）。

### 【设计建议 D3】入队笔记不进时间流

排队期间，两条笔记在时间流里**完全不可见**，唯一线索是输入框下方一个灰色小计数器。用户刚断网写完的第一反应是"我这条是不是没了"。更合适的做法是：入队即以"待同步"态的卡片形式进入时间流顶部（本地占位，flush 后原地替换为服务端行），让"什么都能丢"在断网时也具备可见的即时反馈。影响核心主线：否（不丢数据），但直接削弱"能丢"的心理确定性。

### 5.1 【P1-1】`PATCH /api/notes/:id` 绕过统一敏感管道——R121 同型「另一个入口」攻击成功

先复核 R122 声称的入口覆盖，**逐入口构造含真实形态秘密值的语料实测**（账号 `[QA-R123]-sec`）：

| 入口 | 是否过统一管道 | 生产实测结果 |
|---|---|---|
| 速记 `POST /api/notes` | ✅ | `is_sensitive=1`、`content='[加密内容]'`、`content_enc='v1:…'`、`title=NULL`【D1 实查】|
| 浏览器扩展 `source=extension`（复刻 `extension/utils/api.ts` 真实请求体）| ✅ | 同上，D1 内 `content='[加密内容]'` / `enc='v1:…'` / `title=NULL` |
| 微信 `POST /api/ingest/wechat` | ✅ | `is_sensitive=true`、tags 只留主题词「Wi-Fi」、`title=null` |

| 导入 `POST /api/import` | ✅ | 加密入库 |
| 备份恢复 `POST /api/backup/restore` | ✅ | 加密入库（**R121 的 P1 已闭环**）|
| **`PATCH /api/notes/:id`（content）** | ❌ | **明文入库、`is_sensitive=0`、AI 生成的 title 直接把用途写出来（"路由器管理口令"）** |
| **`PATCH /api/notes/:id`（title/tags，目标已是敏感笔记）** | ❌ | **秘密值原文写进 `title` 与 `tags`** |
| **`POST /api/notes/batch`（加标签）** | ❌ | **秘密值原文作为标签挂到敏感笔记上** |

攻击构造与观测（`sec_test2.py`，秘密值为一次性 QA 串）：

1. 新建普通笔记「今天天气不错」→ 再 `PATCH content` 为「路由器管理口令改成了 R123Pch8Ze52kv，记一下」。响应 200，`is_sensitive=false`；D1 实查 `content` 为**明文**、`content_enc=NULL`，`title` 被 AI 重算成「路由器管理口令」，并且**已生成 `note_embeddings` 行、图谱里生成了含秘密值的实体**。
2. 对一条**已正确加密**的敏感笔记 `PATCH {title:"邮箱密码 R123Ttl4Ry26mb", tags:["邮箱","R123Ttl4Ry26mb"]}`→200 原样落库；再 `POST /api/notes/batch` 给它加标签 `R123Btg6Qm19ho`→`affected:1`。**正文加密照旧，元数据全裸。**
3. 出口扫描（8 值 × 12 出口）命中原文的出口：`GET /api/notes` 列表、`GET /api/tags` 标签云、`GET /api/export`、`GET /api/backup` zip、关键词搜索、`POST /api/ask`。

代码根因【代码证据】：`sensitiveIngestGate()`（`backend/src/ingest.ts`）本身写得很干净，但它是**被调用的工具**而不是**必经的关口**——只有 `createNote()` 及 import/restore 里显式调用了它。PATCH 路由（`backend/src/index.ts` §1335–1470）自己拼 SQL：

```ts
if (typeof body.content === "string") {
  if (wantSensitive && c.env.SUINIAN_ENC_KEY) { /* 加密 */ }
  else { sets.push("content = ?", "content_enc = ?"); binds.push(body.content, null); }
}
```

`wantSensitive` 取自"用户显式传的 `is_sensitive`"或"这条笔记原来的 `is_sensitive`"，**从不对新内容重跑检测**；title/tags 的洗净只在 `is_sensitive` 由 false 翻 true 且用户**没有**显式传 title/tags 时才执行。也就是说：编辑期的敏感性判定完全依赖客户端诚实上报，而写入期是 fail-open。

影响核心主线：**是**。用户在 Web 端编辑一条旧笔记补上密码，是"什么都能丢"的正常用法；结果这条秘密值明文入库、进嵌入、进图谱、进备份 zip，且没有任何提示。

### 5.2 架构评价：高内聚，但收口位置错了——"如无必要勿增实体"这次是"必要的实体没建"

- 内聚性：✅ `ingest.ts` 把"检测 → 加密 → 占位 → 洗 title/tags → 标 `needs_retriage`"五件事收在一个纯函数里，`detectSensitive`（高精度）/`maybeSensitive`（宽松+待复判）两档策略也表达清楚，`opts.rejudge` 的语义（是否还会有 AI 复判兜底）是对的抽象。R122 这一步本身是加分项。
- 结构性风险：❌ 它挂在**服务层的一条分支**上，而不是**所有笔记内容写入的必经路径**上。判据很简单：**判断一个新入口是否安全，必须去读那个入口的代码**——这正是 R119/R121/R123 连续三轮都能在"另一个入口"上打穿的原因（R119 导入、R121 恢复、R123 PATCH+batch）。
- 因此这不是"实体增得太多"，而是"该建的唯一收口没建"：现在是 `createNote / import / restore / patch / batch` 五处各自决定要不要过闸。建议（不在本轮修复范围）：把 `notes.content/title/tags` 的**所有**写入收敛到唯一的 `writeNoteFields()`，闸门放在它内部，PATCH/batch 也必须经它；或退一步在 DB 层加 fail-closed 校验（`is_sensitive=0` 的行若 `detectSensitive(content)` 为真则拒写/标 retriage）。收敛后实体数**减少**而不是增加。
- 同型缺口盘点（本轮已实测，供修复时一并覆盖）：`PATCH content`、`PATCH title/tags`、`POST /api/notes/batch` 标签。

## 六、设计质疑：2 个此前未审流程深挖

### D1（设计建议）手动分类纠偏回路：用 `meta LIKE '%"category":true%'` 找"用户纠正过的样本"

`loadCategoryCorrections()`（`backend/src/triage.ts`）把用户最近的手动分类当 few-shot 喂给分拣 prompt，方向完全正确（让 AI 别重复同一类误判），但三处值得反问"是否真的最适合"：

1. **样本来源用 SQL 字符串匹配 JSON**：`WHERE meta LIKE '%"category":true%'`。这是把 JSON 的内部结构编码进 SQL 字面量——`manual_override` 一旦改名或嵌套层级变化，查询不会报错，只会**静默返回 0 条**，纠偏能力无声消失且无任何监控。更合适：`meta` 里的 override 提升为独立列（`category_source TEXT`）或独立表，既可索引也不怕结构漂移。
2. **只有正样本，没有"AI 原来答错成什么"**：现在喂给模型的是"这句话 → 正确类别"，而模型真正需要的信息是"这句话你判成了 expense，其实是 transfer"。押金/借还这类**方向性**错误，正样本远不如"错→对"对照有效。建议记录纠正前的 AI 判定（一列即可），few-shot 用对照式。
3. **"手动"的定义过宽**：`skipTriage` 的创建、扩展 popup 里默认选中的分类、MCP 显式传 category，全部被记成 `manual_override.category=true`，与"用户主动纠正一次误判"混为一谈。扩展的下拉框只要有默认值，就会持续往纠偏池里灌噪声（见 D2）。建议只把"**改变了已有 AI 判定**"的那次编辑计入纠偏样本。

### D2（设计建议）扩展保存流程：两段写入 + 静默吞掉第二段

`extension/utils/api.ts` 的 `saveNote()` 先 `POST /api/notes`，再对同一条发 `PATCH {category}`，并且：

```ts
await apiFetch(`/api/notes/${id}`, { method: "PATCH", body: JSON.stringify({ category }) })
  .catch(() => undefined); // 保存已成功，分类补写失败不阻断
```

反问三次：

1. **是否真的最适合用两段写入？** 不是。创建接口本就接受 `category`（MCP 走的就是这条路），扩展没有任何理由把它拆成两次网络往返。两段式带来：非原子（第二段失败=用户选的分类丢失）、多一次限流配额、多一次可能触发 AI 重算、以及**必须走 PATCH——恰好是 §5.1 里唯一没有敏感闸门的入口**。收藏网页正文里带凭据的情况并不罕见。
2. **失败静默是否可接受？** 不。注释说"保存已成功，分类补写失败不阻断"——但用户看到的是"已保存"，而他明确选的分类没有生效，且**永不重试、无任何提示**。要么合并进创建请求（首选），要么失败时降级提示"已保存，分类未设置"。
3. **顺带的副作用**：这条 PATCH 无条件写 `manual_override.category=true`，于是"用户没动过下拉框的默认值"也会被当成一次人工纠正进 D1 的 few-shot 池，慢性污染分拣偏好。

两条建议合起来只需**减少**一次请求，属于典型的"如无必要勿增实体"。

## 七、缺陷清单与「可公开推广」评定

R122 四项修复复核结论：统一敏感管道 ⚠️ **创建族六入口全部真实生效，但编辑族（PATCH/batch）未覆盖**（P1-1）；transfer 退款语义 ✅ 真实生效（21/22，残留见 P2-2）；PWA 离线队列 ✅ **真实生效**（入队/离线刷新/自动补发/无重复全过）；语音 `raw_transcript` 洗净【未验证】（本轮未构造语音上传，无一手证据，不作结论）。

**可公开推广评定：暂不建议。** 找回主线 86.7% 的命中率、模糊记忆式提问 93.3%、多跳 100%，已经具备对外讲"可靠找回"的底气；离线队列与 transfer 口径两项也已达标。但两处必须先修：

1. **P1-1**：公开推广会带来"编辑旧笔记补密码"这类最普通的用法，明文落库 + 进备份 zip 属于隐私事故级别，且修复成本低（收口一处）。
2. **P1-2**：新用户最爱问的正是"我一共记了多少条""这周记了什么"，一次自信错答直接否掉核心承诺；正确答案已在 `stats` 里，接一条精确路径即可。

P2 项可在推广后的短周期迭代中处理，不构成阻塞。
