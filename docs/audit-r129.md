## 六、设计质疑（2 个未审流程深挖）

### 6.1 问答召回架构：会话式重写 + 语义 top-k 的枚举盲区

现状（`backend/src/ask.ts` + index.ts ask 路由）：问题经历史重写 → 时间短语解析 → 财务/计数/极值等精确 SQL 路由 → 否则语义召回 top-k + 关键词命中校验。这套"能 SQL 化就绝不让 LLM 猜"的分层设计本身是对的（R107→R126 持续演进的正确方向），但本轮实测暴露了精确路由覆盖面的一个结构性缺口：

- **枚举类主题问题（"我看过什么书/去过哪些地方"）落在两头之间**：它不是计数（countQueryIntent）、不是时间窗枚举（enumListIntent 只认"都记了什么"句式），只能走语义 top-k——而宽泛主题词的 embedding 在小语料下区分度差，被高频主题压过（R8 实证）。
- 是否真的最优？不是。更好的方式：主题枚举意图与计数意图共用同一套主题词剥离逻辑（askTopicTerms 已有），识别出"枚举+主题词"后先做 **关键词/标签 LIKE 全量匹配**（书→tags/正文 LIKE），语义召回只做补充排序。这与既有 fail-closed 哲学同构，不新增实体，只是把已有的 noteHitsTopic 从"事后校验"前移为"召回通道"。低耦合：改动局限在 ask 路由的召回选择处。
- 序数追问（R9"第二本"）依赖上一轮枚举成功，属同一缺口的连带故障，修复枚举后自然缓解；不建议为序数单独增加状态实体。

### 6.2 第三方导入（Notion/Obsidian/Apple Notes zip）：静默丢弃口径

现状（`backend/src/import-zip.ts`、`import.ts`）：解析器设计整体克制（复用 ImportItem 单一实体、资产上限防 R2 洪泛、失败逐条记 failures），但三处**静默丢弃**与产品"什么都能丢进来（且不丢失）"的承诺有张力：`[源码]`

- 图片资产超限（每条 >3 张、全局 >100 张、单张 >5MB）时：正文里保留 `【图片：name】` 占位标记，但字节被丢弃，且**不记入 failures**——用户看到标记会以为图在，实际永久丢失。对比：R128 备份侧同类问题用 `attachments_redacted` 做了可观测化，导入侧应同样在 stats 里加 `assets_dropped` 计数（或逐条 failures），口径统一、零新实体。
- `MAX_IMPORT_ITEMS=2000` 截断：超出部分直接不解析，结果里 total=2000 看不出被截断。大 vault 迁移用户会静默丢笔记。至少应在 stats 返回 truncated 标记。
- Notion CSV 行与同名 md 页去重靠"标题相等"（`mdTitles.has(name)`），同名不同内容的数据库行会被误跳过——概率低，列为 P2 观察项。
- 是否真的最优？分层（zip 解析→ImportItem→runImport 统一入库）是高内聚低耦合的好设计，无须重构；问题只在"丢弃必须可观测"这一条产品纪律上没有贯彻到导入侧。

### 6.3 顺带确认：备份→恢复闭环（正面评价）

恢复路径对"脱敏备份回灌"做了 fail-closed：占位符敏感笔记跳过并计入 `sensitive_skipped`，避免生成永久丢明文的壳笔记；敏感笔记按 created_at+解密内容去重。`[源码]` 该闭环设计与 R128 导出侧口径对齐，无需整改。
