**这是本轮最重要的发现：**

- pre-R294 的降级逻辑是「判别器不可用 → 整答案保守隔离」，所以它在 unavailable 态 **0 泄漏**（代价是善意语料 130/130 全被隔离，见 §3）。
- R294 把降级隔离改成「先看答案有没有代码面痕迹，有才行级隔离」。于是**凡是「没有代码面痕迹」的恶意载体（散文型、注音/摩斯型、分片型、标签字符型、密文型），在判别器不可用时直接原样输出**。
- 换句话说，R294 不是「把 fail-open 收口了」，而是**把 fail-open 从「判别器零命中」这一个口，挪到了「判别器不可用」这个口**，并且新口子更危险 —— 判别器不可用是可被攻击者主动制造的（拖慢/打满上游），而零命中不是。

**【实测】** 关于自报 2（内核否决）：上表 online-empty 的 10/13 条泄漏载体，`globalExecDangerReason()` 全部返回 `null`（见 §2.2 内核列），因此 `index.ts` 里那段 `if (out.length === 0) { const veto = globalExecDangerReason(answer); ... }` 对它们**一条都救不到**。否决逻辑本身工作，但它保护的是「内核本来就能识别的」那一类，与漏面正交。

**【实测】** `exec_guard_degraded` 是否**无条件**在判别器不可用时置真：**不是**。降级标记与行级隔离绑定在同一条「代码面痕迹」前置条件上，痕迹判负时既不隔离、也不打降级标记 —— 用户看不到任何「本次判定降级」的提示，答案看起来和正常态一模一样。

**【实测】** 两态互斥：online-hit 与 unavailable 的标记未同时出现，未发现「先泄漏后撤回」。
**【实测】** 残片：未发现只剩标点/角标的残片答案（R278 的残片兜底仍生效）。

### 2.4 R294 自报基线「24 泄漏 / 180 观测」的口径核对

**【推断】** 我无法用 R294 自己的语料复现出「24」这个数（那需要跑 R294 的 `r294-eval-data.ts`，属于「只复跑对方脚本」，本轮明确禁止作为验收依据）。用**同一批我自己的语料**在 pre-R294 与 R294 上各跑一次（上表），得到的对比是 **31 → 46（变差）**，与 R294 自报的 **24 → 0（变好）** 方向相反。差异的可解释来源：R294 的语料以「有代码面痕迹」的载体为主，正好落在新兜底判据覆盖的那一半；我的语料刻意补齐了「无代码面痕迹」的另一半。**结论：R294 的 leak=0 不是错报，但它的语料不能代表载体空间，用它做发布门是不安全的。**

## 7. E + G：性能与全量回归

### 7.1 性能（生产，HTTP 层）

| 场景 | n | 中位数 |
|---|---|---|
| 首屏（Web 根文档） | 5 | **90 ms** |
| 登录 `/api/auth/login` | 5 | **292 ms** |
| 注册 `/api/auth/register` | 5 | **324 ms** |
| 问答 · 确定性路径（财务/列举） | 12 | **≈220 ms** |
| 问答 · AI 路径（`/api/ask` 非流式） | 6 | **≈3.3 s** |
| 问答 · SSE 首字节 | 3 | 471 / 1727 / **3845 ms** |

AI 路径 Server-Timing 分段（6 次采样的区间与中位数，ms）：

| 段 | 区间 | 中位 | 说明 |
|---|---|---|---|
| `route` | 360–1198 | ~430 | 与 `kwext` 数值几乎相同 → **推断二者并行** |
| `kwext` | 407–1198 | ~480 | 同上 |
| `sem`(`embed`+`scan`) | 119–1357 | ~180 | 命中缓存时很快 |
| `graph` | 344–652 | ~480 | 串行 |
| `dirext` | 313–857 | ~680 | 串行 |
| `conaud` | 346–809 | ~480 | 生成后审计（流式下是 `pre-delta gate`，351–479ms） |
| **`gen`** | **1362–4372** | **~1700** | **占比最大** |
| `execcls` | 0–2573 | 0 | 仅当答案含代码面才触发；触发时 **+2.6s** |
| `total` | 2659–7897 | **~3.3s** | |

**【实测】瓶颈定位与到 1.5s 的路径（按性价比排序）：**

1. **`graph`(480) + `dirext`(680) 串行接在 route/kwext 之后 —— 省 ~1.1s，风险最低。** 二者输入只依赖问句与关键词，不依赖彼此，完全可以和 `sem` 一起并行。这是纯编排改动，不改判据，**不降低任何安全性**。
2. **`conaud`(480) 与流式重叠 —— 省 ~0.4s 感知。** 流式路径已有 `pre-delta gate`，但它挡在首个 delta 之前；改成「先流式、逐段审计、发现问题即中断并替换」需要谨慎（会引入「先泄后收」风险），**不建议**为 0.4s 冒这个险。改为**只对含代码面的答案做全量前置审计、其余流式并行**是折中。
3. **`execcls` 触发时 +2.6s —— 这是最坏体验的来源。** 判别器串在生成之后、交付之前。可以在生成阶段就把「答案是否含代码面」的判断提前（生成第一段时即可判定），与生成并行发起判别，省下几乎全部 2.6s。
4. **`gen` ~1.7s —— 只能靠换更小的模型或压缩输出长度，风险最高**（直接影响答案质量），不建议在当前质量水平下动。

**结论：1.5s 是可达的，但只对确定性路径与「不含代码面」的 AI 路径成立。** 做完 1+3 后，AI 路径预期 total ≈ `max(route,kwext,sem,graph,dirext)` ~0.7s + `gen` 1.7s + `conaud` 0.5s ≈ **2.9s → 并行化后 ≈2.4s**，仍达不到 1.5s；**要真到 1.5s，必须动 `gen`**（更小模型 / 更短输出 / 流式首 delta 提前）。**因此：把目标改成「SSE 首 delta ≤1.5s」是可达的、且是用户真正感知的指标；把「total ≤1.5s」当目标是不现实的**，除非放弃当前生成质量。

另外**【实测】**：`/api/ask` 有速率限制，连续 13 次提问后返回 **429**（约 4 分钟窗口）。这对正常用户没影响，但对评测脚本是硬约束，也是本轮 G 部分跑不完的直接原因。

## 10. 缺陷分级

### P0（发布阻塞）

- **P0-1 判别器不可用时的安全回归。** 无代码面痕迹的恶意载体（散文型/注音/摩斯/分片/U+E0000 标签字符/密文型）在降级窗口原样输出：unavailable 态泄漏 **0/60（pre-R294） → 23/60（R294）**。且此态下 `exec_guard_degraded` **不置真**，用户毫无感知。判别器不可用是攻击者可主动制造的。 → §2.3

- **P1-4 裸「X月」不披露年份**：「12月」静默回退去年，与「去年12月」输出完全相同。 → §6 #4/#5
- **P1-5 门控/兜底对 U+E0000 标签字符零覆盖**：`INVISIBLE_CARRIER_RE` 未含 `U+E0000–U+E007F`。 → §2.2
