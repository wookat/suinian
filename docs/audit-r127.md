## 五、设计质疑：两个未审过的流程深挖

### 5.1 D1：备份/导出的敏感边界漏了"附件原件"（P1-1 根因）

R126 把敏感闭包从"5 个列"扩到"派生明文字段"（`raw_transcript`/`image_description`/`file_excerpt`/`link_excerpt`），方向正确。但备份构建器（`backup.ts`）里，敏感笔记走打码分支后，**紧接着无条件把该笔记的全部附件塞进 `media/`**：

- 【生产实测】含密码 deploy.txt 的敏感笔记：`notes.json` 中 content/title/tags/meta 全部打码，zip 内 `media/2f9f578f.../0-deploy.txt` 3939 字节原文完整可读
- 追问"是否真的最适合"：敏感的**定义源**往往就是附件本身（截图里的密码、文件里的凭据）。正文是派生物都加密了，原件反而明文带出——闭包画反了。更好的方式：敏感笔记的附件在默认备份中跳过并在 manifest 记数说明，`include_sensitive` 开启时才带；改动集中在 backup.ts 一处分支，不新增实体

### 5.2 D2：附件生命周期缺对账层（如无必要勿增实体的反面案例——该有的层没有）

上传（先 R2 后 D1 行）、删笔记、注销三条路径各自操作 R2，删除均为 `waitUntil(...).catch(console.error)` fire-and-forget：

- 任一环节失败（如 R2 删除超时、D1 行写入失败）都会产生永久孤儿，且无人知晓——本轮实测的 3 个 08-07 孤儿即为证据（对应 user 与 attachments 行都已不存在，说明当时清理链路断在 R2 段）
- 高内聚视角：R2 键名已内嵌 `user_id`/`note_id`，对账所需信息齐备；一个低频 cron（列 R2 → 对 attachments 差集 → 删除超过宽限期的孤儿）即可闭环，复用现有 cron 骨架，不引入新存储
- 反例校验：不建议改成同步删除（拖慢注销主路径、且 R2 偶发失败会让注销失败），异步+对账兜底是更适合的组合
