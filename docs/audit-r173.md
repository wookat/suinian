### P1（明显损伤体验或正确性，影响核心主线）

**P1-1 财务极值确定性路由丢弃主题限定成分，单轮/多轮均稳定答错**【生产实测，影响核心主线「可靠找回」】

- 复现 1（单轮）：账号内有 3 条键盘支出（599/458/2200，另有机票 3480）。问「我买过的键盘里最贵的是哪一把」→ 答「你金额最大的一笔支出是 ¥3480 …买了去东京的机票」，且以「以上为数据库精确查询结果」背书。
- 复现 2（多轮）：先问「我都买过哪些键盘」（枚举正确返回 3 条），追问「里面最贵的是哪一个」→ 同样答机票 3480。换措辞「这些键盘里哪个最贵」同样复现。3/3 稳定。
- 归因（源码）：`backend/src/ask.ts` `financeExtremeIntent()` 只识别「最贵/最大一笔 + 方向」，不提取主题限定词；`backend/src/index.ts` L2894-2928 的极值 SQL 只有 user/时间/category 过滤，无主题过滤。单轮时「买」字直接命中门槛；多轮时原问题无财务词，改写器把历史里的「买键盘」补进 recallQuestion 后命中 `financeExtremeIntent(recallQuestion)`。限定成分（键盘）被静默丢弃，答案却以「精确查询」口径输出——错误 + 过度自信双重伤害。
- R172 留观项归因结论：所谓「多轮枚举追问误路由」的稳定复现形态即此——追问中的极值措辞把对话主题作用域丢给了全局财务极值路由。纯枚举追问本身未复现误路由（「那我都买过哪些键盘」多轮下路由正确，见第三节）。
- 是否影响核心主线：**是**（找回环节给出确定性口吻的错误答案，比「没找到」更伤信任）。

## 三、留观项：多轮枚举追问误路由——复现与归因

- 纯枚举追问未复现误路由：演化问答后追问「那我都买过哪些键盘」→ 正确落枚举路由（3 条，确定性口径）；演化问答后追问「都有哪些？帮我列一下」→ 改写继承演化语境走 LLM 综合（合理，非误路由）。
- **稳定复现的是极值型追问**：枚举键盘后追问「里面最贵的是哪一个」/「这些键盘里哪个最贵」→ 全局财务极值路由，答成机票（见 P1-1）。3/3 复现，且单轮带「买」字即可触发，不依赖多轮。
- 归因结论：误路由不是「枚举意图判错」，而是**确定性路由族对限定成分（主题作用域）无组合能力**——改写器忠实地把历史主题补进 recallQuestion，但极值路由的 SQL 无处安放这个主题，静默丢弃。修复方向见第七节·深挖二。

## 四、ask 体感与 SSE 流式评估（建议 + 论证，未实施）

### 实测等待体验

- 确定性路由（枚举/财务/统计）：0.15s ~ 2.2s，体感良好，无需流式。
- LLM 生成路由：6.8s ~ 13.6s（附录 C）；等待期整屏只有 spinner，无进度、无法取消、答案一次性出现。10s+ 的空白等待在移动/微信场景极易被判定为「卡死」。

### Server-Timing 归因（生产实测两个样本）

| 阶段 | 样本 A（演化，6.62s） | 样本 B（多轮追问，13.45s） |
|---|---|---|
| rewrite | 0 | 3634 |
| sem+embed+scan | 306 | 330 |
| kwext | 511 | 2000（顶到预算帽） |
| graph+hop | 1216 | 519 |
| **gen** | **4871（74%）** | **7204（54%）** |

生成不可压缩（模型侧），改写在多轮下最高再加 3.6s——**总时长无法优化到 3s 内，体感只能靠流式解决**。

### SSE 方案论证（建议）

1. **只流式 LLM 生成分支**：确定性路由已 <2.2s，保持整段返回；`POST /api/ask` 加 `Accept: text/event-stream` 协商，不破坏现有客户端（Android/MCP/微信桥不升级也能用）。
2. **事件序列**：`meta`（路由类型 + 检索完成，此时约 1.5-6s，用户先看到「已找到 N 条相关笔记」）→ `delta`×n（生成 token 流，Workers AI 与 DeepSeek 均支持 stream:true，Workers 原生支持流式 Response）→ `done`（携带最终全文 + references）。
3. **引证正确性权衡**：R172 的 q56 引证补全在生成完成后运行，流式期间正文里的 [n] 标号可能与最终引证表不一致 → 建议 `done` 事件下发带最终引证的全文做一次性替换（用户先看到内容流动，结束瞬间标号定稿），不牺牲引证确定性。
4. **取消**：前端 AbortController → Workers 请求取消传播，等待期提供取消按钮（P1-2 直接诉求）。
5. **收益量化**：首内容可见时间从 6.8-13.6s 降到约 2-6s（检索完成即有 meta 反馈，首 token 到达即有正文流动），P95 完成时间不变但「空白等待」消失。
6. **成本**：后端 ask 出口改造一处 + web 问答面板消费 SSE；不新增实体（无新服务/表），符合「如无必要勿增实体」。

## 七、设计深挖（2 个未审流程）

### 深挖一：导入后处理管线——「已分类」被当成「已处理」

- 现状：导入笔记 category 置 NULL 入库，cron 以 `category IS NULL OR needs_retriage=1` 为队列扫描条件逐步分拣（控 AI 配额，本意合理）。
- 质疑：**队列成员资格复用了业务字段**。用户在 cron 处理前手动改分类（导入后整理是高频动作），笔记即离队，金额/币种/商家/标题/疑问标记全部永久跳过，且无任何提示；财务聚合从此永远「另有 N 笔未识别出金额」。生产实测复现（Lofree 599 案例，P2-1）。窗口期 = 导入到 cron 扫到的全部时间，批量导入几百条时窗口以小时计，命中概率不低。
- 是否真的最适合？否。「用户编辑永远赢」原则（R126）赢的应该是**用户改过的字段**（category），不是「整条笔记放弃处理」。
- 更好方式（按侵入性排序）：a) applyTriage 已有 manual_override 字段级跳过能力，让手改分类的导入笔记保留 `needs_retriage`（改分类的 PATCH 分支不清除该位即可），cron 照常提取金额/标题、跳过 category——复用现有机制，不增实体；b) 至少在 UI 上对「未处理完的导入笔记」手改分类时提示「AI 还未提取金额等信息，改分类将跳过」。

### 深挖二：确定性问答路由族的作用域组合缺陷

- 现状：ask 有一族确定性路由（财务极值/聚合/环比/统计/枚举），各自用正则独立判定意图后直接出 SQL。时间限定有统一通道（parseTimeRange），**主题限定没有任何通道**：「键盘里最贵的」= 「最贵的」。而答案措辞统一以「以上为数据库精确查询结果」背书。
- 质疑：确定性路由的设计初衷是「SQL 能精确回答的绝不让 LLM 猜」（R148，方向正确），但**「精确」的前提是问题被完整翻译成了 SQL**。当限定成分被静默丢弃时，输出是「精确执行了错误查询」，比 LLM 猜错更危险——用户会因「精确查询」口径而不加怀疑（P1-1 实测：答案自信地给出错误的 3480）。多轮场景改写器把历史主题补进问题后，该缺陷被系统性放大。
- 更好方式：给确定性路由加一道「限定成分守门」——判定命中极值/聚合意图后，从问题中剥掉意图词与时间词，剩余实义词（如「键盘」「咖啡」）即未消化的限定成分：a) 首选把它作为 LIKE 过滤并入 SQL（枚举路由已有同款关键词过滤能力，复用即可）；b) 并不上 SQL 的（语义类限定）fail-open 回普通召回；c) 兜底至少改措辞为「全部支出中金额最大的一笔」如实声明口径。三层都不增新实体，与既有 fail-closed 哲学一致。
