## P1-1 财务「比较类」问题绕过确定性聚合，总支出漏项算错（影响核心主线：可靠找回）

【生产实测】主测账号写入 7 笔支出（含 CNY 10618.50）、3 笔收入（含 CNY 24932.60）后：

- q1「这个月我总共花了多少钱收入多少」→ 走确定性聚合路径，回答精确：
  「本月共记录 7 笔支出、3 笔收入。CNY：支出 ¥10618.50，收入 ¥24932.60；USD：支出 $12.99」✔
- q9「这个月我是赚得多还是花得多」→ 走 LLM 自由算术路径，回答：
  「本月收入有 18500 元，支出包括房租 3200、餐饮 78.5、交通 126、咖啡 35 和健身房年卡 4680，
  总支出为 8119.5 元」——**漏掉显示器 2499 等支出项与部分收入，收入/支出两个总数都错**
  （结论方向"赚得多"碰巧正确）。

同一份账本，两种问法两个答案。`buildFinanceAggAnswer` 的确定性路径只覆盖直接统计问法，
"比较/哪个多"类问法落入 LLM 召回笔记后自由加总——召回 top-N 截断 + LLM 算术双重不可靠。
**建议（改法留给修改轮）：比较类意图并入确定性聚合路由（识别"赚得多/花得多/入不敷出"等问法，
用 SQL 聚合结果做比较后再措辞），LLM 只负责措辞不负责算术。**

## P2 列表

### P2-1 GBK 编码 CSV 提取成乱码（影响核心主线：什么都能丢——丢进去即损毁）

【生产实测】上传 GBK 编码 CSV（中文表头「日期,类别,金额,备注」）→ 201 接收，但提取文本为
`����,���,���,��ע`，AI 摘要与检索均基于乱码，原始语义不可找回（原件存 R2 可救）。
【源码】`backend/src/files.ts` 只 `new TextDecoder("utf-8")` 解码。中文用户从老版 Excel/WPS
导出 CSV 默认 GBK 是高频场景。建议：BOM 嗅探 + UTF-8 解码失败率启发式回退 GBK
（Workers 的 TextDecoder 支持 gbk）。

### P2-2 扩展名优先于 MIME，伪装扩展名导致错误解析（什么都能丢：轻微）

【生产实测】XLSX 内容 + `.csv` 扩展名 + XLSX MIME 上传 → 按 CSV 文本解析二进制 ZIP，提取出乱码。
【源码】`detectFileKind` 扩展名命中即返回，MIME 仅兜底。建议：对 csv/xlsx 这类可嗅探格式先看
magic bytes（`PK\x03\x04` 即 zip/xlsx），扩展名与内容冲突时以内容为准。

### P2-3 大文件 AI 摘要数字失实（AI 整理：摘要忠实性）

【生产实测】6000 行 CSV（518KB）上传成功、全文提取成功，但 AI 摘要称「总共231行」。
摘要基于截断后的 excerpt 让 LLM 自数行数，必然失实。建议：行数/列数等结构性数字由解析器
确定性统计后注入摘要 prompt，禁止 LLM 自己数。

### P2-4 标签重命名不覆盖回收站，恢复后标签口径分裂（可靠找回：轻微）

【生产实测】笔记（标签「咖啡」）软删入回收站 → 全局重命名 咖啡→咖啡馆（affected=2）→
恢复该笔记 → 其标签仍为「咖啡」，与全局「咖啡馆」分裂，按新标签筛选找不回这条。
【源码】`retagUser` 查询条件 `deleted_at IS NULL`。建议：重命名/删除包含回收站行
（软删恢复是产品承诺的一部分），或恢复时对账。

### P2-5 refetch-link / retry-media / tags rename+delete 无限流（成本/滥用面）

【生产实测】同一链接笔记连续 6 次 `POST /api/notes/:id/refetch-link` 全部 200（191-224ms），
无节流；每次触发服务端出站抓取 + AI enrich。【源码】这 4 个端点均无 `checkRateLimit`
（对比：note_write 60/min、ask 15/min、bulk_ingest 有限流）。仅限本人 token 可用，
无越权面，但可被脚本刷出站流量与 AI 配额。建议并入 note_write 或单独低频桶。

### 5.1 标签重命名/删除流程（/api/tags/rename、/api/tags/delete）

现状【源码+生产实测】：改名即全量重写每条笔记的 tags JSON（逐行 UPDATE）；改到已有标签自动合并
（实测 猫咪→咖啡 合并后 count=3 正确）；`to` 长度 32 上限、空参 400 边界正确；敏感行 tags 经
sanitizeSensitiveTags 单口收敛（好设计）；LIKE 预筛 + `current.includes(from)` 精确复核，
子串误匹配防住了。

追问"是否真的最适合"：
- **回收站盲区是真缺陷**（P2-4，生产已复现）：软删恢复是产品承诺，重命名却只作用于未删行。
- 逐行 UPDATE 无事务：中途失败留下半改状态，且 affected 计数不可信。当前单用户几百条量级
  可接受，但该端点无限流（P2-5），恶意循环 rename 会放大 D1 写入。
- 更优方向：tags 若继续存 JSON 列，rename 可用 D1 batch（一次事务）；或维护 note_tags 关系表
  一条 UPDATE 完成——但为改名单独建表违背"如无必要勿增实体"，**维持 JSON 列 + batch 事务即可**。

### 5.2 失败重试流程（refetch-link / retry-media 原地重试）

现状【源码+生产实测】：retry-media 从 R2 存档原件原地重跑提取（用户不需重传），成功后清空旧分拣
重新走完整管线（fail-closed 敏感预检保留）；仅 `extract_failed` 状态可重试，成功后再调返回 400
「该笔记无需重试」——状态机干净。refetch-link 对链接笔记重抓标题/正文。

追问"是否真的最适合"：
- 原地重试 + 原件存档的设计本身**优于常见的"让用户重新上传"**，与"什么都能丢"主线一致，认可。
- 缺口是两端点均无限流（P2-5，生产实测 6 连发全 200）：refetch-link 每次触发服务端出站抓取
  与 AI enrich，是账号内的成本放大器。
- retry-media 对 GBK 乱码类"提取成功但内容错误"的笔记无法重试（status=ok 即 400）——若按 P2-1
  建议修解码，存量乱码笔记需要一条重提取通道（可复用现有 retriage 管线做一次性回填）。
