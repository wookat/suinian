### P2-1 台账聚合金额污染主题极值答案（新发现，影响「可靠找回」准确性）
【实测】问「键盘里最便宜的是哪一把」→ 答 ¥356「近期消费」。¥356 是多行台账（键盘 199+鼠标 99+午饭 38+打车 20）的聚合合计，非一把键盘的价格；真实最便宜键盘是 ¥458 Keychron K3。确定性 SQL 按关键词匹配到含「键盘」行的台账笔记后，把聚合金额当单笔支出参与极值比较。
- 影响：主题极值答案可能错（方向性：聚合值通常偏大，故「最便宜」更易被污染；「最贵」侧 2200>356 恰好正确）。全局极值不受影响（356 也是一笔真实支出总额）。
- 建议：台账类笔记（`parseLedgerTable` 命中多行）打 meta 标记，主题极值查询排除聚合笔记或下钻行级金额。

## 六、设计深挖（2 个未审过流程）

### D1 台账笔记的「一条笔记 = 一笔聚合金额」数据模型，是否真的最适合？
现状：多行 CSV 台账整体入库为一条 expense 笔记，`fixLedgerAmount` 兜底出聚合合计。这保证了「入账合计正确」（R178 目标），但把 N 笔异质消费压成一个不可分割的金额原子——P2-1 的极值污染是必然产物，同理「上月餐饮花了多少」这类分类聚合也会把台账里的午饭算不进餐饮。
更好的方式？两个方向：(a) 行级展开——台账笔记入库时同步产出行级子记录（note meta 里存 rows 数组即可，无需新表，如无必要勿增实体），财务查询按行参与、按父笔记去重；(b) 最小改动——meta 标记 `ledger: true`，主题极值/分类统计跳过聚合笔记。建议先做 (b)（一行 WHERE 条件收口），(a) 待真实用户台账使用频次证明必要后再做。

### D2 乐观锁把「系统丰富写」与「用户内容写」混在同一版本空间，是否真的最适合？
现状：异步分拣/链接摘要等系统写全部 `updated_at = datetime('now')`，与用户编辑共用同一 CAS 版本。用户（或脚本）在分拣窗口内基于旧版本编辑，会收到「该笔记刚被其他设备修改」——但其实没有任何其他设备，也没有内容冲突（分拣只动 category/meta，编辑动 content）。eval 竞态即此问题的直接暴露；真实用户「记完立刻改错字」同样会踩中。
更好的方式？内容版本与丰富版本分离：CAS 只对用户可编辑字段（content/tags/todo_due…）的版本号生效，系统丰富写不 bump 该版本（或 PATCH 冲突时做字段级合并——检查 base 与 head 的差异是否与本次编辑字段相交，不相交则自动重放）。冲突文案「其他设备」也应改为如实描述。此改动收益是消除一类必然发生的假冲突，成本是一列或一次 diff 判断，值得列入下轮。
